# Авторитетні ринкові дані та валютні курси

## Мета

Замінити технічний demo-індекс `6000` на відтворюваний контур ринкових
довідкових даних. Кожне збережене значення має бути перевірюваним: зрозуміло,
що саме воно означає, звідки надійшло, у якій валюті та на який момент було
актуальним.

Ця задача не робить demo-прогноз з wizard ринковою ціною і не переписує
історичні demo-звіти 2023–2025.

## Контекст і залежності

- Вихідний контракт: [ADR-002 — фінансовий контракт](../decisions/002-financial-calculation-contract.md).
- `StoneValuation` уже відокремлює майбутні `market_reference`,
  `system_prediction`, `expert_appraisal`, `asking_price` та `sale_price`.
- Приватне редагування та комерційний стан реалізовано в 080; ринковий
  snapshot інтегрується з цим flow окремо, без зміни historical report data.
- Admin UI з [100](./100-profile-and-admin-ui.md) має бути споживачем цього
  контуру, а не місцем, де з'являються неверсіоновані суми.

## Межі

### 1. Окремо визначити два типи джерел

1. **Ринкове джерело діамантів**: ліцензований або явно дозволений провайдер
   довідкових котирувань. До погодження провайдера не виконувати scraping,
   не припускати ліцензію та не називати demo-індекс ринковим котируванням.
2. **Валютний курс**: окреме джерело, потрібне лише якщо система показує або
   розраховує суми поза базовою валютою котирування. Курс USD/UAH не є ціною
   діаманта; для нього потрібні власні джерело, дата, timezone та правила
   округлення.

На старті погоджуємо: провайдера, його умови використання, базову валюту,
одиницю котирування (наприклад, сума чи сума за карат), частоту оновлення,
ліміти API та поведінку при помилці.

### 2. Історичні незмінні snapshot-и

- Додати через окрему Alembic-міграцію модель(і) для ринкового котирування та
  валютного курсу з `Decimal`/`Numeric`, кодом валюти, одиницею, провайдером,
  зовнішнім ідентифікатором/версією, часом отримання та часом актуальності.
- Додавати новий snapshot, а не оновлювати або перераховувати старий.
- Збережена у звіті оцінка посилається на конкретний snapshot і зберігає її
  тип (`market_reference`, `expert_appraisal` тощо). Новий курс або
  котирування не змінює минулу оцінку автоматично.
- Порівняння історичної оцінки зі свіжим ринком — окремий аналітичний сценарій
  з явним вибором дат, а не прихований background rewrite.

### 3. Оновлення і доступ

- Спочатку реалізувати захищену ручну дію admin: отримати, валідувати та
  зберегти новий snapshot; показати джерело, timestamp і останній успішний
  стан.
- Помилка провайдера не стирає останнє відоме коректне значення та не створює
  псевдоактуальну ціну. Логи не повинні містити API-ключі або повні секретні
  відповіді.
- Лише після цього погодити scheduler: частоту, retry/backoff, rate limits,
  observability та сповіщення про застарілі дані.
- API/frontend відображають provenance і відрізняють «немає актуального
  джерела», «застарілий snapshot», «довідкова ринкова ціна» та «експертна
  оцінка».

### 4. Дані, UI і межі MVP

- Legacy `DiamondReport.price` і 1 000 demo-записів лишаються
  `legacy_unclassified_value` з `USD … d`; backfill можливий тільки окремо
  погодженим планом після підтвердження походження кожного значення.
- Демо-прогноз wizard лишається незбереженим і позначеним `d` до появи
  перевіреної версіонованої моделі або правила.
- Публічний паспорт не показує суми, доки окрема policy не дозволить конкретний
  тип оцінки та необхідні метадані.

## Критерії готовності

- Письмово зафіксовані провайдери, ліцензія/умови, валюта, одиниця, частота і
  policy застарівання даних.
- Міграція створює тільки нові структури й не змінює legacy/demo значення без
  окремого дозволу.
- Усі суми передаються як `Decimal`/рядки, не `float`; правила округлення
  перевірені.
- API повертає походження, валюту, одиницю та дату snapshot-а; неможливо
  подати технічний індекс як ринкове котирування.
- Ручне admin-оновлення, відмова/timeout провайдера й відсутній курс покриті
  unit/API-тестами з mock провайдера; інтеграційні тести не звертаються до
  зовнішнього API.
- Автоматичний scheduler, якщо буде погоджений, має окремі перевірки retry,
  rate limit та не переписує історію.

## Відкриті рішення

1. Яке авторитетне й доступне джерело ринкових котирувань можна законно
   використати для цілі Diamant ID?
2. Чи потрібен у локальному MVP показ USD/UAH, чи поки достатньо базової USD?
3. Яку саме величину джерело надає: готову ціну каменю, ціну за карат,
   діапазон за 4C або індекс? Як вона зіставляється з атрибутами звіту?
4. Чи створює admin market-reference автоматично для draft, чи експерт явно
   прикріплює конкретний snapshot під час оцінки?
5. Коли ручний flow буде стабільний, чи потрібне оновлення за розкладом і з
   якою частотою?
