# 146 — Незбережене введення майстра звіту

## Мета

Не допустити випадкової втрати введених у «Новому звіті» даних при переході,
reload або зміні locale, не створюючи приховану server-side чернетку.

## Поточний стан і проблема

`POST /reports` створює draft лише після явного підтвердження користувача. Це
правильна доменна межа, але незбережені значення живуть лише у DOM і зникають
після навігації. Така поведінка неприйнятна для тривалого експертного введення
і не дозволяє виконати контракт 145 про безпечне перемикання мови.

## Погоджений напрям

- Зберігати незбережений стан тільки у `sessionStorage` поточної вкладки:
  ключ має включати schema-version та поточного user ID. Дані не синхронізуються
  між вкладками, акаунтами чи пристроями.
- Відновлювати поля й поточний wizard step після reload/повернення на сторінку;
  перед першим відновленням показувати зрозумілий вибір «Відновити / Почати
  заново». Не відправляти значення на API під час автозбереження.
- Показувати browser leave-warning, коли є локальні незбережені зміни. Це лише
  додатковий захист: браузер не гарантує текст warning і не спрацьовує в усіх
  mobile-сценаріях.
- Після успішного `POST /reports` очищати стан лише після отримання успішної
  відповіді. Явна дія «Очистити введення» потребує підтвердження.
- Файли не кладуться у Web Storage: browser не може безпечно й надійно
  відновити `File` objects. UI чесно повідомляє, що приватні вкладення треба
  додати знову після відновлення форми.
- Не зберігати JWT, пароль або інші session credentials у цьому механізмі.
  Авторські коментарі лишаються тільки на пристрої в межах вкладки до явного
  save; це обмеження треба пояснити в UI.

## Залежності

- Виконати до 145: i18n перемикач має використовувати той самий state-preserving
  механізм і не очищувати форму.
- Не залежить від ML, PostgreSQL або staging.

## Перевірки

- Unit/DOM: serialize/restore, schema-version, user isolation, explicit clear,
  successful save clear та відсутність file/JWT у payload.
- Playwright: внесення даних → navigation/reload → restore; cancel restore;
  successful save → немає stale restore; desktop і mobile leave behavior у
  межах можливостей браузера.

## Поза межами

- Автоматичне створення server draft, collaborative editing, offline sync,
  міжпристроєве відновлення або відновлення файлів.
