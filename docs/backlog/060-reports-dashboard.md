# Dashboard звітів

## Мета

Перетворити dashboard із демо-розмітки на робочий список звітів.

## Scope

- Дані лише через приватний `/reports` та актуальний API-клієнт, без
  демо-рядків, legacy `/diamonds/` і дубльованих довідників у frontend.
- Контракт списку повертає `items`, `total`, `page`, `page_size` і
  `total_pages`; обмежує `page_size`, застосовує allow-list сортувань і не
  віддає необмежену вибірку.
- Пошук лише за номером звіту; фільтри окремо за lifecycle
  (`draft/review/issued/void`) і ринковим станом каменю
  (`not_for_sale/available/reserved/sold/withdrawn`). Продаж не є lifecycle
  статусом звіту.
- `gemologist` бачить лише власні звіти; `admin` бачить усі та може обрати
  конкретного експерта. Список експертів береться з API.
- Dashboard містить зрозумілі loading, empty, error і forbidden-стани,
  server-driven пагінацію та зберігає поточні параметри в URL.
- У рядку є колонка «Дії» з доступною службовою кнопкою `⋮` та меню
  `Переглянути`, `Редагувати`, `Друк`. Це точкові дії; чекбокси й bulk-операції
  не входять до задачі. Посилання і недоступні дії можуть вести лише до
  запланованих зрізів 080, доки їхні маршрути не реалізовані.

## Рішення та межі

- API списку не повертає фінансові значення: `price` — legacy-величина без
  погодженого фінансового контракту для UI. Dashboard показує доменно безпечні
  поля звіту й каменю; ціни й продажі будуть розширені після окремого рішення.
- Пагінація працює сторінками, а не через прихований frontend `skip`.
  Сервер може внутрішньо застосувати offset, але клієнтський контракт цього не
  розкриває.
- Зміна lifecycle, редагування та друк не реалізуються тут: ця задача створює
  лише коректну навігаційну оболонку для 080.

## Критерії готовності

- Dashboard показує фактичні дані API і зберігає фільтри в URL у межах сценарію.
- Є API-перевірки pagination/search/filter/RBAC, DOM-перевірки станів і один
  цільовий E2E-flow dashboard для авторизованого користувача.
