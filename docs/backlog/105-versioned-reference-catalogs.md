# Версії правил IDC і довідників оцінювання

## Мета

Зробити правила, за якими інтерпретуються оцінки у Diamant ID, прозорими та
історично стабільними. Задача не має перетворити MVP на повну реалізацію
стандарту IDC або дати адміністратору можливість непомітно змінювати формулу
виданих звітів.

Початкове нормативне джерело для аналізу — *IDC Rules for Grading Polished
Diamonds, 6th edition, July 2013*. Поточний `idc-demo-v1` — свідомо спрощене
правило застосунку, а не заява про повну сертифікаційну відповідність цьому
документу.

## Поточний стан і проблема

- Серверний `DiamondCalculator` для `idc-demo-v1` використовує лише table,
  depth, crown angle та pavilion angle для системного `Proportions`; системний
  `Final Cut` отримується з Proportions, Polish і Symmetry.
- Polish і Symmetry обирає експерт; для видачі також зберігаються окремі
  експертні значення Proportions і Final Cut.
- Код версії правила вже записується у report як
  `calculation_rule_version = "idc-demo-v1"`, але немає реєстру версій,
  джерела, області застосування, policy оновлення чи повного test-vector
  набору.
- UI читає назви багатьох значень з поточних `reference_values` та
  `grade_mappings`. Їхнє просте редагування не повинно змінювати зміст уже
  створених report, public passport або PDF.

## Межа відповідності IDC 2013

У межах задачі створюється матриця «вимога IDC 2013 → поточна підтримка →
обмеження / наступний крок». Попередня оцінка така:

| Частина | Поточний стан MVP | Висновок |
| --- | --- | --- |
| Proportions | Частковий, детермінований demo-розрахунок за 4 параметрами | Не відтворює повну таблицю IDC: бракує, зокрема, girdle, culet, інших геометричних і візуальних факторів. |
| Polish | Експертний grade з контрольованої шкали | Відповідає природі експертної оцінки, але не автоматичній перевірці всіх умов IDC. |
| Symmetry | Експертний grade з контрольованої шкали | Відповідає природі експертної оцінки, але без фіксації всіх спостережень та вимірів IDC. |
| Final Cut | Системний результат і окрема expert-confirmed величина | Потрібно прибрати дублювання джерел істини: підсумок має обчислювати сервер. |
| Nature, treatment, report disclosure | Частково є як довідникові значення й поля report | Потрібна окрема явна матриця public/private disclosure; це не робить MVP повним IDC report. |

Поки матрицю й test vectors не завершено, інтерфейс і документація мають
використовувати формулювання «системний розрахунок за `idc-demo-v1`», а не
стверджувати повну відповідність IDC 2013.

## Рішення щодо блоку «Висновок та підтвердження»

Для одного звіту кожна оцінка повинна мати одне зрозуміле джерело:

1. **Polish** і **Symmetry** — прямі експертні оцінки. Вони залишаються
   селектами з версіонованої шкали, але без другого поля «підтверджений».
2. **Proportions** — система показує свій `idc-demo-v1` результат лише як
   підтримку рішення. Експерт обирає одну оцінку Proportions; UI пояснює, що
   вона може відрізнятися від спрощеного системного результату.
3. **Final Cut** не вводиться вручну та не «підтверджується» окремим select.
   Сервер детерміновано обчислює його за активним ruleset із експертних
   Proportions, Polish і Symmetry. UI показує read-only
   «Підсумковий Cut за експертними оцінками».
4. Якщо у майбутньому знадобиться override підсумку, це буде окремий
   exception-flow з обов'язковою причиною, автором, audit event і видимою
   позначкою у звіті — не прихований ручний select.

Така схема відокремлює системний preview від професійного рішення експерта і
не дає `Final Cut` суперечити складовим grades.

## Запропонований механізм оновлення IDC

Не реалізовувати універсальний UI-редактор формул або числових меж. Нова
редакція IDC може кардинально змінити вхідні параметри, терміни, процедуру та
правила комбінування grades; редагований поріг у адмінці не є безпечним
механізмом для такого оновлення.

Замість цього:

- ruleset є незмінним записом/артефактом із `ruleset_id`, назвою, джерелом,
  редакцією документа, датою чинності, сферою підтримки, версією алгоритму та
  поясненням обмежень;
- report при створенні назавжди прив'язується до активного ruleset;
- новий IDC ruleset вводиться окремою task/release: аналіз змін у джерелі,
  зміни коду й схеми за потреби, приклади на межах діапазонів, review та явне
  активування для **нових** report;
- historical report, паспорт і вже завантажений PDF не перераховуються;
  переоцінка створює новий report/revision із посиланням на попередній;
- для `idc-demo-v1` ruleset прямо фіксуються обмеження, а не приховуються за
  словом «IDC».

## Довідники: що може контролювати admin

| Група | Політика |
| --- | --- |
| System-locked | ролі, lifecycle, RBAC і механізми обчислення — не редагуються у UI. |
| Ruleset-scoped | шкали grades, їх назви, допустимі disclosures, терміни ruleset — версіонуються та активуються тільки в контрольованому release-flow. |
| Admin-local | identification methods, лабораторія/місце видачі, шаблонні фрази, переклади та інші локальні метадані — можуть мати version/reason/source/effective date, якщо впливають на нові report. |
| Ринкові дані | не входять до 105: джерело, FX і snapshots залишаються у 110. |

Навіть для admin-local каталогу зміна не повинна переписувати відображення
історичних виданих документів: потрібні immutable release і прив'язка report
до використаної версії.

## Етапи

### A. Рішення та аудит (перший інкремент)

- Підготувати матрицю відповідності IDC 2013 для підтримуваних полів і
  розрахунків.
- Зафіксувати правила назв та UI для expert grades / системного preview /
  підсумкового Final Cut.
- Описати `idc-demo-v1` як ruleset, його джерело, вхідні дані, межі та
  обов'язкові test vectors.
- Уточнити контракт historical stability для report, public passport і PDF.

### B. Мінімальна технічна основа

- Додати immutable registry ruleset-ів і безпечний зв'язок нових report із
  конкретною версією.
- Перенести Final Cut у server-derived результат експертних grades.
- Версіонувати лише ті каталоги, які реально впливають на значення report;
  додати API/RBAC/audit, міграцію та регресійні тести.

### C. Майбутня зміна редакції IDC

- Проводити окремим рішенням після аналізу нового первинного документа.
- Не припускати, що нові межі можна застосувати без нових полів, алгоритму чи
  звітування.

## Не входить

- Повна сертифікаційна реалізація IDC 2013 або юридичне підтвердження
  відповідності.
- Автоматичний backfill, перерахунок чи перекласифікація historical reports.
- Вільний UI-редактор формул, меж або комбінування grade.
- Авторитетні ціни й FX з 110.
- Публічні media з 130.

## Критерії готовності

- Є перевірювана матриця поточної відповідності IDC 2013 та меж MVP.
- Для кожного grade у виданому report визначене одне джерело істини; Final Cut
  не можна зробити суперечливим ручним введенням.
- Кожен ruleset має автора/джерело, дату чинності, межу застосування й
  regression test vectors.
- Зміна діє лише на нові report; historical report, public passport та PDF
  зберігають історичний зміст.
- API не дає переписати published ruleset або обійти RBAC; критичні сценарії
  покриті API/unit/frontend regression-тестами.
