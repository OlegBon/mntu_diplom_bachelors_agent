# Якість текстових полів звіту

## Призначення

Diamant ID показує пояснювані сигнали заповнення для приватних полів «Метод
ідентифікації», «Висновок щодо ідентифікації» та «Коментар експерта». Це
допоміжна перевірка перед ручним рішенням експерта або admin, а не автоматична
експертиза каменю.

Сигнали не блокують створення, збереження або перехід статусу, не змінюють
текст і не впливають на IDC, Final Cut, ціну, паспорт, PDF чи рейтинг людей.

## Що саме перевіряється

Серверний модуль `backend/narrative_quality.py` однаково обробляє українські
та англійські слова Unicode-aware правилом. Він може позначити:

- незаповнене необов'язкове поле;
- однозначний службовий placeholder (`—`, `n/a`, `тест` тощо);
- дуже короткий текст;
- структурне надмірне повторення слова;
- великий текст, який варто переглянути на структурність;
- відсутній висновок за selected рівня підтвердження «Підтверджено».

Це консервативні review signals, а не пороги «добре/погано». Лише фахівець
вирішує, чи є текст доречним для конкретного каменю.

## Приватність та доступ

`GET /reports/{report_id}/narrative-quality` доступний лише користувачу, який
вже має приватний доступ до цього operational звіту. Він повертає назву поля,
код і пояснення сигналу, але не нове сховище тексту.

`GET /statistics/narrative-quality` доступний лише admin. Відповідь не містить
тіла тексту або уривків: лише кількість непорожніх значень, медіану/середнє
слів і символів без пробілів, а також три найкоротші й найдовші записи як
`report_id`, дата та лічильники. Посилання у private UI ведуть до вже
авторизованого звіту. Для кожного поля також є `candidate_count`,
`non_empty_count` і `empty_count`; для порожніх значень UI показує до трьох
private `report_id`/дат, щоб їх можна було знайти без розкриття тексту.

`GET /demo/datasets/{dataset_id}/narrative-quality` використовує той самий
metadata contract і renderer, але доступний лише opted-in admin та тільки для
manifest-authorized isolated synthetic dataset. Він ніколи не читає operational
звіти; посилання ведуть лише до private `demo-report-detail` цього dataset.

## Робочі фільтри пропусків

У «Всі звіти» та «Демо-звіти» admin у секції «Текстові поля» обирає одне чи
кілька current полів: метод, висновок або коментар експерта. Перемикач
«Порожні / Заповнені» явно визначає, що шукати; за замовчуванням лишається
сумісний режим «Порожні». Кілька полів працюють як «хоча б одне з полів».
Вибір зберігається в URL/API як повторюваний `empty_narrative` і allow-listed
`narrative_presence=empty|filled`. Порожність або заповненість визначається
тим самим server-side Unicode/whitespace `normalize_text`, що й analytics.

Operational список має ще опцію «Подія зміни статусу без коментаря»: вона
шукає хоча б один `status_changed` event з порожнім `reason`; за date filter
враховуються event-и в цьому date slice. Це не current поле report. Synthetic
`DemoWorkflowEvent` не має текстових коментарів, тому опція у demo чесно
недоступна, а не перетворює кожну synthetic подію на «порожню».

У розширеному фільтрі це одна shared Pug-секція на одному рядку з діапазоном
дати: перша колонка містить method/conclusion, друга — expert comment/status
event, третя — явний перемикач режиму й коротке пояснення семантики. Заголовок
має ті самі розмір і візуальну вагу, що й інші labels фільтра; desktop/tablet
центрує action-зону, а mobile складає три колонки вертикально та використовує
спільний full-width pattern кнопок. Це лише presentation contract: кількість
вибраних checkbox-ів і URL/API semantics від layout не залежать.

## Семантика дат і історії

Поточна схема не зберігає revision history трьох полів звіту. Тому за
`date_from` / `date_to`:

- метод, висновок і коментар експерта — це їхні **поточні** значення у звітах,
  створених у періоді;
- коментар до зміни статусу — це append-only `ReportEvent.reason` для подій,
  що сталися у періоді.

Для demo поточні значення беруться зі synthetic звітів, датованих у періоді.
Synthetic status events не мають `reason`, тому опція status-transition не
моделюється в жодному режимі.

Отже статистика не називає поточний текст historical snapshot. Якщо знадобиться
історія редакцій, її слід проєктувати окремо з consent, retention і доступами.

## Межі майбутнього NLP/ML

Не надсилайте приватні тексти до зовнішньої LLM або NLP-сервісу без окремої
письмової policy. Будь-який ML-контур можливий лише після data contract задачі
151: consent/privacy, human-labelled corpus, українська й англійська оцінка,
versioned artifact та human review. «Тональність», правда/неправда й оцінка
якості експерта не є результатами цього механізму.
