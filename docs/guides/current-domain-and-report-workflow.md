# Звіт про діамант: від створення до публічного PDF-паспорта

**Стан коду:** 25 вересня 2026 року. Це guide фактично реалізованого локального
MVP, а не опис майбутнього production-процесу.

Документ пояснює весь робочий шлях звіту: хто створює та погоджує дані, що
потрапляє до публічного паспорта, як працюють код/посилання/QR/PDF і де
закінчується поточна реалізація. Технічні деталі API наведено в
[architecture.md](../architecture.md), структура БД — у
[db-schema.md](../db-schema.md), а майбутні роботи — у
[work_plan.md](../work_plan.md) та backlog.

## 1. Коротка схема процесу

```text
gemologist: wizard → draft → review
                              ↓
admin:                 повернути в draft / видати / анулювати
                                           ↓
                                  опублікувати паспорт
                                           ↓
                         код + пряме посилання + QR + PDF
                                           ↓
                          покупець перевіряє public passport
```

Ключове розділення:

- **Звіт** — приватний робочий запис для експерта й admin.
- **Публічний паспорт** — обмежена анонімна проєкція лише виданого та
  опублікованого звіту.
- **PDF-паспорт** — файл, який admin генерує на запит із тієї самої поточної
  публічної проєкції; це не окрема копія даних у БД і не юридично незмінний snapshot.

## 2. Ролі й доступ

| Хто | Може |
| --- | --- |
| `gemologist` | Створювати власні чернетки, бачити лише власні звіти, редагувати власні `draft`, передавати їх на перевірку, працювати з private-вкладеннями своїх `draft`. |
| `admin` | Бачити всі звіти, редагувати будь-який `draft`, передавати `draft` на перевірку, повертати з `review` у `draft`, видавати або анулювати звіт; публікувати, перевипускати й відкликати паспорт виданого звіту, завантажувати PDF. |
| Гість / покупець | Не має доступу до `/reports`. Може відкрити тільки чинний публічний паспорт за кодом, посиланням або QR. |

Private API потребує JWT. Видимість або приховування кнопки у frontend не
замінює перевірку ролі на сервері.

## 3. Створення звіту

Експерт працює у wizard `/create-report.html`. У ньому завжди три кроки, щоб
форма була читабельною на desktop і mobile:

1. **Основні 4C.** Дата дослідження / оцінки, форма, вага, колір і чистота.
2. **Геометрія (IDC).** Розміри, table/depth, crown/pavilion, girdle, culet,
   polish, symmetry та fluorescence. Сервер на льоту обчислює IDC preview.
3. **Висновок та медіа.** Походження, ознаки обробки, рівень і метод
   ідентифікації, висновок, коментар і приватні plotting/фото.

`GET /reports/next-id` показує наступний номер для зручності, але не резервує
його. Лише `POST /reports` призначає остаточний послідовний `DR-…`.

### Незбережене введення майстра

До явного натискання «Зберегти чернетку» дані не є звітом і не надсилаються на
сервер. Щоб експерт не втрачав введення після переходу зі сторінки або reload,
браузер зберігає поточні поля та крок майстра лише в `sessionStorage` поточної
вкладки. Ключ містить версію формату й ID поточного користувача: дані не
переносяться між вкладками, обліковими записами або пристроями.

Після повернення майстер не відновлює значення мовчки: спершу показує вибір
«Відновити» або «Почати заново». «Очистити введення» також потребує
підтвердження. Після успішної відповіді `POST /reports` локальний стан
видаляється. Перехід внутрішнім посиланням спершу показує проектну модалку:
дані залишаються в цій вкладці й можуть бути явно відновлені після повернення.
Для reload, закриття вкладки та інших сценаріїв, які браузер не дає
перехопити інтерфейсом застосунку, лишається стандартне browser-попередження;
його конкретний текст і сама підтримка залежать від браузера, особливо на
mobile.

Файли plotting і фото не зберігаються у Web Storage та після відновлення мають
бути вибрані повторно. Механізм ніколи не зберігає JWT, пароль або інші
облікові дані й не створює приховану server-side чернетку.

Дата дослідження в UI за замовчуванням дорівнює поточній даті, але експерт може
вказати фактичну дату оцінки. Вона відрізняється від технічних `created_at` та
`updated_at`.

### Приватні поля звіту

| Група | Поля поточного контракту |
| --- | --- |
| Ідентифікація | `report_id`, статус, автор, дата створення/оновлення, `examination_date`, дата й автор видачі. |
| Фізичні дані каменю | Форма, вага, колір, чистота, довжина/ширина/глибина, table %, depth %, crown angle, pavilion angle, girdle thickness, culet size, fluorescence. |
| Висновок експерта | Походження, treatment status, identification status, метод ідентифікації, текстовий висновок, коментар експерта. |
| IDC і експертні grades | System Proportions, System Final Cut, immutable версія правила; експертна оцінка Proportions і server-derived підсумковий Final Cut. Значення відображаються текстом із серверного `grade_mappings`, хоча в БД зберігаються числові коди. |
| Комерційний стан | `not_for_sale`, `available`, `reserved`, `sold`, `withdrawn`. Він не є оцінкою, ціною чи статусом lifecycle. |
| Приватні вкладення | Plotting і фото каменю з MIME, розміром, hash і metadata; тіла файлів лежать поза БД та Git. |
| Аудит | Append-only події `created`, `report_updated`, `status_changed`, включно з причиною переходу, якщо її вказали. |

Новий звіт починається як `draft` із `market_status=not_for_sale`.

### Активний час автора draft

Після першого збереження draft його автор-`gemologist` може редагувати report
detail. Саме тоді — не у ще незбереженому wizard — frontend починає
server-timed сесію лише після введення, кліку, фокусу чи іншої дії користувача.
`created_at`, `updated_at`, різниця між save і legacy `evaluation_time_sec` не
є active-time.

- Видима вкладка надсилає start/resume, heartbeat і save; сервер зараховує не
  більш як 60 секунд між сигналами за своїм годинником.
- Прихована вкладка, page close, offline або відсутність сигналу не додають
  час: lease спливає через 75 секунд. Offline-час пізніше не надсилається.
- На один report і його автора може існувати лише одна активна вкладка. Нова
  вкладка завершує попередню сесію як `replaced`, тому два вікна не подвоюють
  метрику.
- «Скасувати» завершує сесію pause; передавання `draft → review` завершує її
  server-side як finish. Admin може редагувати draft, але це не приписується
  автору-експерту й не є active-time експерта.

У вкладці «Аналітика» active-time показується тільки admin як operational
metric: завершені сесії, total/average/median і три найкоротші/найдовші з
посиланням на report. Він не є рейтингом чи оцінкою продуктивності. Старі
звіти не отримують штучно реконструйованого часу.

### Час до першого збереження майстра

Це інший показник, ніж active-time: він вимірює server-timed elapsed time від
першої взаємодії у видимому «Новому звіті» до успішного `POST /reports`.
Frontend не передає власний timestamp. Замість цього він отримує короткоживучий
`POST /report-wizard-sessions` lease з серверним `started_at` і передає лише
його UUID разом із create payload.

- Під час успішного save сервер у тій самій транзакції перевіряє власника та
  строк lease, записує `first_save_started_at` і `time_to_first_save_seconds`
  у новий report, а lease видаляє.
- Один експерт має лише один live wizard lease: дія в іншій вкладці замінює
  попередній. Старий UUID не блокує save, але звіт буде створено без метрики.
- Offline, покинутий або прострочений майстер також не блокує save і не дає
  показника. Це свідомо краще за недостовірний клієнтський час.
- У «Деталях експерта» admin бачить count, total, average і median окремо від
  active-time існуючої чернетки. Показник не є рейтингом продуктивності й не
  backfill-иться для historical reports.

### IDC та системний preview

`POST /reports/preview` не зберігає звіт. Серверний `DiamondCalculator`
визначає Proportions за геометрією, а Final Cut — як найгіршу з оцінок
Proportions, Polish і Symmetry. Це спрощений системний розрахунок Diamant ID,
методична основа якого — *IDC Rules for Grading Polished Diamonds, 6th edition
(2013)*, а не повна експертна методика або сертифікація IDC. Внутрішній код
ruleset `idc-demo-v1` не показується користувачу; межі та процес майбутнього
оновлення описані в [guide ruleset](./idc-demo-v1-ruleset.md).

Збережені system grades не є чергою на фоновий перерахунок. `draft` може
отримати актуальну версію ruleset лише через штатне збереження; `review`,
`issued` і `void` не переписуються. Legacy projection-колонки існують для
сумісності та історії, але не є джерелом UI або експертного рішення. Старий
масовий скрипт перерахунку вилучено: будь-яке майбутнє порівняння починається
лише з read-only dry-run, обмеженого scope і плану відновлення даних.

Якщо в admin policy є обраний провайдер та його застосовний `approved` snapshot,
цей самий preview показує `USD … of`: системний довідковий орієнтир із поточних
параметрів каменю. Це **не** ринкова, експертна, продажна або транзакційна ціна.
Preview не створює `StoneValuation`, не фіксує курс НБУ та може змінитися до
збереження чернетки. Під час `POST /reports` сервер повторно застосовує policy
й уже зберігає незмінний орієнтир із provenance; за ввімкненого FX — також
зафіксований еквівалент UAH.

### Ринковий орієнтир і USD/UAH

Ринкові орієнтири — окремі private-величини: автоматичний
`system_market_reference` і вручну підтверджений admin-ом `market_reference`.
Жоден не є оцінкою експерта, продажною пропозицією, транзакційною або ціною
продажу. Вони не замінюють legacy demo `price` і не потрапляють до public
passport або PDF.

Кожен новий immutable орієнтир також потрапляє до private «Історії змін»
з сумою, провайдером і номером snapshot-а: автоматичний запис має подію
«Системний довідковий орієнтир додано», ручний — «Довідковий орієнтир
підтверджено адміністратором». Повторне збереження з тими самими market
inputs не створює ні valuation, ні дубль події.

| Позначка | Де видно | Сенс |
| --- | --- | --- |
| `USD … of` у wizard | Майстер нового звіту | Попередній розрахунок за поточною admin policy та approved OpenFacet snapshot; ще не зафіксований у звіті. |
| `USD … of` | Dashboard для підтримуваного нового draft або ручного підтвердження | Довідковий total OpenFacet; detail/popover пояснює, чи його створила система або підтвердив admin. Ручний запис має пріоритет над системним. |
| `—` | Wizard або dashboard | Немає застосовного approved snapshot-а чи ринкового орієнтира. |

#### Приклад: автоматичний орієнтир і ручне підтвердження для `DR-01004`

1. У «Ринкові дані» admin у картці **OpenFacet** натискає «Отримати
   кандидат». Сервер завантажує котирування, зберігає незмінний snapshot із
   URL, методологією, timestamp і checksum. Candidate ще ні до чого не
   застосовується.
2. Admin перевіряє candidate в «Історії знімків» і натискає «Затвердити».
   Лише останній `approved` snapshot активного в policy провайдера може
   автоматично розрахувати системний орієнтир під час створення нового draft
   або зміни його market-вхідних даних.
3. Для supported `natural` diamond backend інтерполює USD/ct, одержує
   актуальний офіційний USD/UAH НБУ й фіксує immutable системний
   `StoneValuation`. Ідентичний набір snapshot-а і вхідних характеристик не
   дублюється. Якщо snapshot, покриття або НБУ тимчасово недоступні, draft
   все одно зберігається без нового `*`.
4. За потреби admin у «Прикріпити орієнтир до звіту» вказує `DR-01004`, обирає цей
   snapshot, додає пояснення застосовності та підтверджує checkbox. Поточний
   adapter дозволяє лише `natural` diamond із підтриманими OpenFacet shape,
   color, clarity і carat anchors. Непідтримуваний або `lab_grown` камінь
   отримує пояснення і reference не створюється.
5. Backend інтерполює OpenFacet USD/ct до total USD за вагою каменю. У цей
   самий момент він заново отримує **офіційний USD/UAH НБУ**, обчислює UAH з
   `Decimal` і зберігає: OpenFacet snapshot, NBU FX snapshot, курс, official
   rate date, USD та UAH. Це одна історична `StoneValuation`.
6. У private detail з’являється структурована картка «Системний довідковий
   орієнтир», а після ручного підтвердження — окрема картка «Підтверджений
   довідковий орієнтир». На dashboard ручний `USD … of` має пріоритет над
   системним `USD … of`; detail/popover пояснює їхню різницю.
   popover показує суму,
   OpenFacet snapshot, UAH еквівалент, курс НБУ, його дату й FX snapshot.

Якщо НБУ недоступний або відповідь некоректна, ручне підтвердження повертає
помилку і не створює reference зі старим курсом; автоматичний крок тихо
пропускається, не блокуючи draft. Новий курс або OpenFacet snapshot ніколи не
перераховує вже збережений орієнтир. НБУ може повертати official rate date
наступного банківського дня — інтерфейс показує саме цю дату.

Кнопка «Оновити зараз» на картці НБУ створює окремий контрольний FX snapshot.
Вона не змінює звіти й не є scheduler-ом; під час actual attach сервер однаково
отримує курс повторно. Дані ринку, NBU та прикріплення доступні тільки admin.

## 4. Статуси звіту та погодження

### Кодування в API та підписи в інтерфейсі

| Код статусу | Підпис у Diamant ID | Коротко |
| --- | --- | --- |
| `draft` | Чернетка | Робочий звіт, який можна редагувати. |
| `review` | На перевірці | Дані заблоковані й очікують рішення admin. |
| `issued` | Видано | Погоджений звіт; доступний public passport. |
| `void` | Анульовано | Остаточно закритий звіт без редагування та public access. |

| Статус | Значення | Хто й що може зробити |
| --- | --- | --- |
| `draft` / Чернетка | Робочий звіт; дані ще можна змінювати. | Owner або admin редагує, додає/видаляє private media, передає у `review`. |
| `review` / На перевірці | Дані заблоковані для редагування й очікують рішення admin. | Лише admin повертає у `draft`, видає або анулює. |
| `issued` / Видано | Звіт погоджено. | Лише admin може анулювати; саме тут доступна публікація паспорта. |
| `void` / Анульовано | Звіт остаточно закрито в поточному MVP. | Редагування, публікація та public access недоступні. |

Дозволені переходи:

```text
draft  -- owner або admin --> review
review -- admin --> draft | issued | void
issued -- admin --> void
```

Перед `review → issued` сервер перевіряє, що експерт задав Proportions. Polish
і Symmetry є прямими оцінками експерта, а Final Cut сервер детерміновано
отримує з цих трьох складових — тому його не можна вручну зробити
суперечливим. Кожна зміна стану створює audit event; коментар до рішення не
обов’язковий технічно, але корисний для повернення або анулювання.

### Приклад: один звіт від створення до паспорта

Нижче — конкретна послідовність для звіту `DR-01001`. Вона описує поточну
реалізовану поведінку, а не бажаний майбутній процес.

1. **Експерт створює чернетку.** У «Новий звіт» він заповнює три кроки,
   перевіряє системний preview `idc-demo-v1`, прикріплює за потреби приватні
   plotting/фото та натискає «Зберегти». Сервер сам призначає остаточний
   `DR-…`; кнопка next ID нічого не резервує. Якщо це перша взаємодія у
   видимому майстрі й save успішний, сервер також фіксує окремий «час до
   першого збереження». Звіт має статус `draft`.
2. **Експерт допрацьовує `draft`.** На сторінці звіту автор або admin натискає
   «Редагувати чернетку». Тут коригуються дані каменю, висновок і коментар.
   Polish та Symmetry — прямі експертні grades. Експерт обирає Proportions;
   «Підсумковий Cut за експертними оцінками» відразу показується read-only і
   буде остаточно порахований сервером під час збереження. В історію додається
   «Дані чернетки оновлено». Лише коли автор-експерт починає дію у редагованій
   чернетці, окремо стартує active-time сесія; вхід у систему, перегляд звіту
   та робота в незбереженому майстрі до неї не належать.
3. **Експерт передає на перевірку.** У блоці «Стан звіту» натискає «Передати
   на перевірку». Поля й вкладення блокуються, статус стає `review`. Автор уже
   не може сам ані редагувати, ані видати чи анулювати звіт.
4. **Admin переглядає `review`.** Admin бачить той самий private report,
   системні та експертні grades, вкладення й історію. Якщо бракує даних або
   потрібна правка, він за потреби пише коментар і натискає «Повернути в
   чернетку»: статус знову `draft`, після чого автор або admin може редагувати
   та повторно передати на перевірку. Це не видаляє історію попереднього
   review.
5. **Admin видає звіт.** Якщо Proportions задано, admin натискає «Видати
   звіт». Сервер ще раз перевіряє допустимий перехід і наявність експертного
   Proportions, фіксує `issued_at` та `issued_by_id`. Статус стає `issued`;
   поля вже не можна редагувати ні експерту, ні admin.
   Пункт «Друк» у меню `⋮` відкриває private detail в новій вкладці та викликає
   системний діалог друку. Це робочий друк внутрішнього звіту, а не документ,
   який передають покупцеві.
6. **Admin передає публічний паспорт за потреби.** Лише для `issued` він
   натискає «Опублікувати паспорт», бачить код, URL і QR та може завантажити
   PDF. В історії показуються зрозумілі події «Публічний паспорт
   опубліковано», «… перевипущено» або «… відкликано».
7. **Відкликання й анулювання.** Перевипуск зразу вимикає старий код/URL/QR і
   створює новий; відкликання вимикає поточний публічний доступ, але лишає
   звіт `issued`. Admin може анулювати виданий звіт (`issued → void`): public
   tokens закриваються, а редагування чи повторна публікація недоступні.
   `void` не повертається в `draft` у поточному MVP; для виправленої оцінки
   створюється новий звіт, а не переписується виданий.

Отже, для одного звіту в «Деталях експерта» можуть з’явитися дві незалежні
метрики: час до його першого збереження і сума завершених active-time сесій
подальшого редагування. Вони не складаються та не використовуються як рейтинг
експерта.

| Статус | Хто бачить private звіт | Хто редагує поля | Доступні переходи |
| --- | --- | --- | --- |
| `draft` | Автор і admin | Автор або admin | Автор/admin → `review` |
| `review` | Автор і admin | Ніхто | Admin → `draft`, `issued`, `void` |
| `issued` | Автор і admin | Ніхто | Admin → `void`; admin також керує public passport |
| `void` | Автор і admin | Ніхто | Немає |

## 5. Публічний паспорт

Admin може опублікувати паспорт **лише** для `issued` report. Сервер створює
випадковий непослідовний `public_id`; це ключ перевірки, а не номер звіту.
Внутрішній `DR-01001` не можна використати для перебору або відкриття
паспорта.

Після публікації в private detail admin бачить:

- код публічного паспорта (`public_id`);
- пряме публічне посилання;
- QR-код, у якому закодоване це посилання;
- кнопки копіювання коду й посилання;
- кнопку завантаження PDF-паспорта;
- дії «Перевипустити» та «Відкликати публікацію».

### Як покупець перевіряє паспорт

Є три однаково чинні канали:

1. Ввести **код** зі сторінки звіту на головній сторінці Diamant ID.
2. Відкрити передане **пряме посилання**.
3. Відкрити посилання після сканування **QR-коду**.

Поле на головній навмисно приймає тільки код. Це робить призначення форми
однозначним; URL та QR вже містять адресу паспорта і не потребують повторного
пошуку. Для `DR-…` головна пояснює, що це внутрішній номер, а не публічний
код.

`GET /public/passports/{public_id}` не потребує JWT. Для неіснуючого,
відкликаного, не виданого або анульованого паспорта сервер однаково повертає
`404`, не розкриваючи причину.

### Поля публічного паспорта і PDF

Browser endpoint і PDF використовують **одну allow-list проєкцію**; PDF не
читає private ORM-поля напряму. Водночас PDF додатково друкує дані, потрібні
для передачі документа.

| Група | Browser-паспорт | PDF-паспорт |
| --- | --- | --- |
| Ідентифікація | Номер звіту, дата видачі, час останнього оновлення публічної проєкції. | Номер звіту, дата видачі, дата дослідження, public code, час формування PDF. |
| Камінь | Форма, вага, колір, чистота, довжина/ширина/глибина. | Ті самі дані. |
| Оцінки | System Proportions, System Final Cut, експертний Proportions і server-derived Final Cut. | Ті самі дані. |
| Висновок | Походження, treatment status, identification status. | Ті самі дані. |
| Передача | Відкривається за URL із QR або за кодом через головну сторінку. | Пряме посилання, QR і надрукований код. |
| Явно публічні зображення | Лише погоджені admin фото каменю та/або схема огранювання. | Той самий чинний набір, окремими пропорційно масштабованими A4-сторінками. |

Публічний паспорт і PDF **не** містять ціну, demo-прогноз, commercial status,
коментарі, текстовий висновок, метод ідентифікації, дані експерта, history,
private media або прямий доступ до private `/reports` API.

### PDF-паспорт

Admin завантажує PDF із detail виданого й опублікованого звіту. Сервер перевіряє
admin RBAC та поточний URL, генерує PDF on-demand і віддає його як attachment.
Файл не зберігається окремо в БД чи storage. Чинні явно опубліковані фото
каменю та схема огранювання додаються після основної сторінки по одному на
сторінку; пошкоджений файл або SHA-256 mismatch просто не потрапляє в PDF.

У PDF QR містить чинне публічне посилання. Український текст рендериться
bundled DejaVu Sans, тому файл не залежить від набору шрифтів на сервері.

## 6. Перевипуск, відкликання та анулювання

| Дія | Що відбувається |
| --- | --- |
| Перевипуск | Старий `public_id`, URL і QR деактивуються; admin отримує нові код, URL, QR і за потреби завантажує новий PDF. Старий PDF фізично лишається у отримувача, але його QR/URL більше не відкриває паспорт. |
| Відкликання публікації | Поточний код, URL і QR одразу стають нечинними; новий PDF не завантажується. Report лишається `issued` і його можна опублікувати знову. |
| Анулювання `issued → void` | Усі активні public tokens деактивуються автоматично; browser-паспорт і нове PDF-завантаження повертають opaque `404`. |

Відкликання не може забрати вже переданий файл із чужого пристрою. Так само,
якщо admin прибирає зображення з паспорта, воно зникає з browser-паспорта й
усіх **наступних** PDF, але не з уже завантажених файлів. Тому PDF показує час
формування, а одержувач має перевіряти актуальність за кодом, URL або QR у
момент перегляду.

## 7. Вкладення та розширення публічних полів

Фото каменю (`stone_photo`) і plotting (`plotting_diagram`) спочатку завжди
**private-only**. Після видачі report admin може окремо опублікувати кожне
таке зображення в блоці «Вкладення» приватного detail. Це не публікує storage:
anonymous browser отримує файл лише через allow-listed URL, прив'язаний до
чинного коду паспорта. `supporting_document` і `instrument_image` не можуть
бути public.

Відкликання паспорта, перевипуск старого посилання або `void` робить media URL
недоступним (404). Публічний endpoint приймає лише JPEG/PNG/WebP, звіряє
збережений SHA-256 і віддає `Cache-Control: no-store`; private filename, hash,
comment та інші metadata у public API не потрапляють. PDF повторює allow-list,
MIME та SHA-256-перевірку перед декодуванням, тому private, revoked або
пошкоджені вкладення в нього не входять.

Потреба додати фото, plotting або інші поля до публічної частини не вимагає
переписувати lifecycle, але потребує окремого security-рішення: явного
allow-list, consent/admin-flow, окремого content endpoint, MIME/hash/cache
перевірок і сценаріїв revoke/void.

Будь-яке інше нове поле для паспорта також має пройти такий порядок:

1. Погодити, чи воно справді публічне, а не лише зручне в private detail.
2. Додати його до явної `PublicPassportView` allow-list проєкції, а не віддати
   ORM-модель або весь звіт.
3. Відобразити узгоджено у browser-паспорті й PDF; будь-яку виправдану
   різницю для передачі документа (як код або дата дослідження) зафіксувати
   явно.
4. Додати API/RBAC/regression тести, включно з reissue, revoke і void, якщо
   поле пов’язане з файлом або публічним URL.

## 8. Dashboard, дані та межі MVP

Dashboard використовує private `GET /reports`: server-side pagination, пошук,
фільтри й сортування. `sold=true|false` є зручною двостановою проєкцією
детального commercial status, а не його заміною. Звіт відкривається через
`/report-detail.html?id=<report_id>`.

### Ринковий орієнтир і курс НБУ

На dashboard колонка «Ціна (USD)» може мати лише один із таких сенсів:

| Вигляд | Значення |
| --- | --- |
| `USD … d` | Legacy demo-значення з навчального набору; не ринкова, експертна чи продажна ціна. |
| `USD … of` | Системний або явно прикріплений admin-ом довідковий OpenFacet market reference. Detail/popover показує його тип; ручний запис має пріоритет над системним і legacy demo. |
| `—` | Немає жодного з наведених значень. |

Натискання відкриває popover з provenance. Для `*` і `of` це також frozen UAH
еквівалент, snapshot OpenFacet, snapshot НБУ, курс та official rate date.
OpenFacet reference не є appraisal, offer, transaction чи sale price.

Як admin прикріплює `of`:

1. На «Ринкові дані» отримує OpenFacet candidate та окремо approve його.
2. Вказує report і пояснює застосовність для конкретного natural stone.
3. Server **саме в цей момент** отримує офіційний USD/UAH НБУ. Успіх створює
   незмінні market та FX snapshots і один `StoneValuation` з USD і UAH.
4. Якщо НБУ недоступний, attach завершується помилкою: старий курс не
   підставляється. Пізніші курси НБУ не змінюють уже прикріплений орієнтир.

Admin може натиснути «Оновити зараз» у картці НБУ для окремого контрольного
snapshot-а. Це не approval, не scheduler і не змінює наявні reports. Для
вихідного/святкового дня НБУ може повернути official rate date попереднього
банківського дня — інтерфейс показує саме цю дату.

Ринкові суми залишаються private: їх немає в public passport, QR і PDF.

Legacy `/diamonds/*` вилучено. Historical legacy-колонки не очищалися та не
перераховувалися. Вони лишаються compatibility-проєкцією до окремого
контрольованого retirement; межу IDC, legacy та ML фіксує
[ADR-004](../decisions/004-legacy-calculation-and-ml-boundary.md).

Поточні automated tests використовують SQLite у пам’яті для backend та mock
HTTP для Playwright. Вони перевіряють RBAC, lifecycle, allow-list, QR/PDF і
code lookup, але не замінюють повний real-browser E2E з MariaDB.
