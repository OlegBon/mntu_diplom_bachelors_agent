# Звіт про діамант: від створення до публічного PDF-паспорта

**Стан коду:** 16 вересня 2026 року. Це guide фактично реалізованого локального
MVP, а не опис майбутнього production-процесу.

Документ пояснює весь робочий шлях звіту: хто створює та погоджує дані, що
потрапляє до публічного паспорта, як працюють код/посилання/QR/PDF і де
закінчується поточна реалізація. Технічні деталі API наведено в
[architecture.md](../architecture.md), структура БД — у
[db-schema.md](../db-schema.md), а майбутні роботи — у
[work_plan.md](../work_plan.md) та backlog.

## 1. Коротка схема процесу

```text
gemologist: wizard → draft → review
                              ↓
admin:                 повернути в draft / видати / анулювати
                                           ↓
                                  опублікувати паспорт
                                           ↓
                         код + пряме посилання + QR + PDF
                                           ↓
                          покупець перевіряє public passport
```

Ключове розділення:

- **Звіт** — приватний робочий запис для експерта й admin.
- **Публічний паспорт** — обмежена анонімна проєкція лише виданого та
  опублікованого звіту.
- **PDF-паспорт** — файл, який admin генерує на запит із тієї самої публічної
  проєкції; це не окрема копія даних у БД і не юридично незмінний snapshot.

## 2. Ролі й доступ

| Хто | Може |
| --- | --- |
| `gemologist` | Створювати власні чернетки, бачити лише власні звіти, редагувати власні `draft`, передавати їх на перевірку, працювати з private-вкладеннями своїх `draft`. |
| `admin` | Бачити всі звіти, редагувати будь-який `draft`, передавати `draft` на перевірку, повертати з `review` у `draft`, видавати або анулювати звіт; публікувати, перевипускати й відкликати паспорт виданого звіту, завантажувати PDF. |
| Гість / покупець | Не має доступу до `/reports`. Може відкрити тільки чинний публічний паспорт за кодом, посиланням або QR. |

Private API потребує JWT. Видимість або приховування кнопки у frontend не
замінює перевірку ролі на сервері.

## 3. Створення звіту

Експерт працює у wizard `/create-report.html`. У ньому завжди три кроки, щоб
форма була читабельною на desktop і mobile:

1. **Основні 4C.** Дата дослідження / оцінки, форма, вага, колір і чистота.
2. **Геометрія (IDC).** Розміри, table/depth, crown/pavilion, girdle, culet,
   polish, symmetry та fluorescence. Сервер на льоту обчислює IDC preview.
3. **Висновок та медіа.** Походження, ознаки обробки, рівень і метод
   ідентифікації, висновок, коментар і приватні plotting/фото.

`GET /reports/next-id` показує наступний номер для зручності, але не резервує
його. Лише `POST /reports` призначає остаточний послідовний `DR-…`.

Дата дослідження в UI за замовчуванням дорівнює поточній даті, але експерт може
вказати фактичну дату оцінки. Вона відрізняється від технічних `created_at` та
`updated_at`.

### Приватні поля звіту

| Група | Поля поточного контракту |
| --- | --- |
| Ідентифікація | `report_id`, статус, автор, дата створення/оновлення, `examination_date`, дата й автор видачі. |
| Фізичні дані каменю | Форма, вага, колір, чистота, довжина/ширина/глибина, table %, depth %, crown angle, pavilion angle, girdle thickness, culet size, fluorescence. |
| Висновок експерта | Походження, treatment status, identification status, метод ідентифікації, текстовий висновок, коментар експерта. |
| IDC і експертні grades | System Proportions, System Final Cut, immutable версія правила; експертна оцінка Proportions і server-derived підсумковий Final Cut. Значення відображаються текстом із серверного `grade_mappings`, хоча в БД зберігаються числові коди. |
| Комерційний стан | `not_for_sale`, `available`, `reserved`, `sold`, `withdrawn`. Він не є оцінкою, ціною чи статусом lifecycle. |
| Приватні вкладення | Plotting і фото каменю з MIME, розміром, hash і metadata; тіла файлів лежать поза БД та Git. |
| Аудит | Append-only події `created`, `report_updated`, `status_changed`, включно з причиною переходу, якщо її вказали. |

Новий звіт починається як `draft` із `market_status=not_for_sale`.

### IDC та демонстраційний прогноз

`POST /reports/preview` не зберігає звіт. Серверний `DiamondCalculator`
визначає Proportions за геометрією, а Final Cut — як найгіршу з оцінок
Proportions, Polish і Symmetry. Це системний розрахунок ruleset `idc-demo-v1`,
а не повна експертна методика IDC 2013. Межі та процес майбутнього оновлення
описані в [guide ruleset](./idc-demo-v1-ruleset.md).

Preview може показувати `USD … d`. Позначка `d` означає детермінований
демонстраційний прогноз: це **не** ринкова, експертна або продажна ціна та він
не записується як ціна звіту. Авторитетні ціни, FX і provenance заплановані в
[110](../backlog/110-authoritative-market-data-and-fx.md).

## 4. Статуси звіту та погодження

| Статус | Значення | Хто й що може зробити |
| --- | --- | --- |
| `draft` / Чернетка | Робочий звіт; дані ще можна змінювати. | Owner або admin редагує, додає/видаляє private media, передає у `review`. |
| `review` / На перевірці | Дані заблоковані для редагування й очікують рішення admin. | Лише admin повертає у `draft`, видає або анулює. |
| `issued` / Видано | Звіт погоджено. | Лише admin може анулювати; саме тут доступна публікація паспорта. |
| `void` / Анульовано | Звіт остаточно закрито в поточному MVP. | Редагування, публікація та public access недоступні. |

Дозволені переходи:

```text
draft  -- owner або admin --> review
review -- admin --> draft | issued | void
issued -- admin --> void
```

Перед `review → issued` сервер перевіряє, що експерт задав Proportions. Polish
і Symmetry є прямими оцінками експерта, а Final Cut сервер детерміновано
отримує з цих трьох складових — тому його не можна вручну зробити
суперечливим. Кожна зміна стану створює audit event; коментар до рішення не
обов’язковий технічно, але корисний для повернення або анулювання.

### Приклад: один звіт від створення до паспорта

Нижче — конкретна послідовність для звіту `DR-01001`. Вона описує поточну
реалізовану поведінку, а не бажаний майбутній процес.

1. **Експерт створює чернетку.** У «Новий звіт» він заповнює три кроки,
   перевіряє системний preview `idc-demo-v1`, прикріплює за потреби приватні
   plotting/фото та натискає «Зберегти». Сервер сам призначає остаточний
   `DR-…`; кнопка next ID нічого не резервує. Звіт має статус `draft`.
2. **Експерт допрацьовує `draft`.** На сторінці звіту автор або admin натискає
   «Редагувати чернетку». Тут коригуються дані каменю, висновок і коментар.
   Polish та Symmetry — прямі експертні grades. Експерт обирає Proportions;
   «Підсумковий Cut за експертними оцінками» відразу показується read-only і
   буде остаточно порахований сервером під час збереження. В історію додається
   «Дані чернетки оновлено».
3. **Експерт передає на перевірку.** У блоці «Стан звіту» натискає «Передати
   на перевірку». Поля й вкладення блокуються, статус стає `review`. Автор уже
   не може сам ані редагувати, ані видати чи анулювати звіт.
4. **Admin переглядає `review`.** Admin бачить той самий private report,
   системні та експертні grades, вкладення й історію. Якщо бракує даних або
   потрібна правка, він за потреби пише коментар і натискає «Повернути в
   чернетку»: статус знову `draft`, після чого автор або admin може редагувати
   та повторно передати на перевірку. Це не видаляє історію попереднього
   review.
5. **Admin видає звіт.** Якщо Proportions задано, admin натискає «Видати
   звіт». Сервер ще раз перевіряє допустимий перехід і наявність експертного
   Proportions, фіксує `issued_at` та `issued_by_id`. Статус стає `issued`;
   поля вже не можна редагувати ні експерту, ні admin.
6. **Admin передає публічний паспорт за потреби.** Лише для `issued` він
   натискає «Опублікувати паспорт», бачить код, URL і QR та може завантажити
   PDF. В історії показуються зрозумілі події «Публічний паспорт
   опубліковано», «… перевипущено» або «… відкликано».
7. **Відкликання й анулювання.** Перевипуск зразу вимикає старий код/URL/QR і
   створює новий; відкликання вимикає поточний публічний доступ, але лишає
   звіт `issued`. Admin може анулювати виданий звіт (`issued → void`): public
   tokens закриваються, а редагування чи повторна публікація недоступні.
   `void` не повертається в `draft` у поточному MVP; для виправленої оцінки
   створюється новий звіт, а не переписується виданий.

| Статус | Хто бачить private звіт | Хто редагує поля | Доступні переходи |
| --- | --- | --- | --- |
| `draft` | Автор і admin | Автор або admin | Автор/admin → `review` |
| `review` | Автор і admin | Ніхто | Admin → `draft`, `issued`, `void` |
| `issued` | Автор і admin | Ніхто | Admin → `void`; admin також керує public passport |
| `void` | Автор і admin | Ніхто | Немає |

## 5. Публічний паспорт

Admin може опублікувати паспорт **лише** для `issued` report. Сервер створює
випадковий непослідовний `public_id`; це ключ перевірки, а не номер звіту.
Внутрішній `DR-01001` не можна використати для перебору або відкриття
паспорта.

Після публікації в private detail admin бачить:

- код публічного паспорта (`public_id`);
- пряме публічне посилання;
- QR-код, у якому закодоване це посилання;
- кнопки копіювання коду й посилання;
- кнопку завантаження PDF-паспорта;
- дії «Перевипустити» та «Відкликати публікацію».

### Як покупець перевіряє паспорт

Є три однаково чинні канали:

1. Ввести **код** зі сторінки звіту на головній сторінці Diamant ID.
2. Відкрити передане **пряме посилання**.
3. Відкрити посилання після сканування **QR-коду**.

Поле на головній навмисно приймає тільки код. Це робить призначення форми
однозначним; URL та QR вже містять адресу паспорта і не потребують повторного
пошуку. Для `DR-…` головна пояснює, що це внутрішній номер, а не публічний
код.

`GET /public/passports/{public_id}` не потребує JWT. Для неіснуючого,
відкликаного, не виданого або анульованого паспорта сервер однаково повертає
`404`, не розкриваючи причину.

### Поля публічного паспорта і PDF

Browser endpoint і PDF використовують **одну allow-list проєкцію**; PDF не
читає private ORM-поля напряму. Водночас PDF додатково друкує дані, потрібні
для передачі документа.

| Група | Browser-паспорт | PDF-паспорт |
| --- | --- | --- |
| Ідентифікація | Номер звіту для читання, дата видачі. | Номер звіту, дата видачі, дата дослідження, public code. |
| Камінь | Форма, вага, колір, чистота, довжина/ширина/глибина. | Ті самі дані. |
| Оцінки | System Proportions, System Final Cut, експертний Proportions і server-derived Final Cut. | Ті самі дані. |
| Висновок | Походження, treatment status, identification status. | Ті самі дані. |
| Передача | Відкривається за URL із QR або за кодом через головну сторінку. | Пряме посилання, QR і надрукований код. |

Публічний паспорт і PDF **не** містять ціну, demo-прогноз, commercial status,
коментарі, текстовий висновок, метод ідентифікації, дані експерта, history,
private media або прямий доступ до private `/reports` API.

### PDF-паспорт

Admin завантажує PDF із detail виданого й опублікованого звіту. Сервер перевіряє
admin RBAC та поточний URL, генерує односторінковий PDF on-demand і віддає його
як attachment. Файл не зберігається окремо в БД чи storage.

У PDF QR містить чинне публічне посилання. Український текст рендериться
bundled DejaVu Sans, тому файл не залежить від набору шрифтів на сервері.

## 6. Перевипуск, відкликання та анулювання

| Дія | Що відбувається |
| --- | --- |
| Перевипуск | Старий `public_id`, URL і QR деактивуються; admin отримує нові код, URL, QR і за потреби завантажує новий PDF. Старий PDF фізично лишається у отримувача, але його QR/URL більше не відкриває паспорт. |
| Відкликання публікації | Поточний код, URL і QR одразу стають нечинними; новий PDF не завантажується. Report лишається `issued` і його можна опублікувати знову. |
| Анулювання `issued → void` | Усі активні public tokens деактивуються автоматично; browser-паспорт і нове PDF-завантаження повертають opaque `404`. |

Відкликання не може забрати вже переданий файл із чужого пристрою. Тому
одержувач має перевіряти актуальність за кодом, URL або QR у момент перегляду.

## 7. Вкладення та розширення публічних полів

Сьогодні plotting і фото з wizard — **private-only**, навіть якщо metadata має
`is_public`. Їх не віддають ні browser-паспорт, ні QR, ні PDF.

Потреба додати фото, plotting або інші поля до публічної частини не вимагає
переписувати lifecycle, але потребує окремого security-рішення: явного
allow-list, consent/admin-flow, окремого content endpoint, MIME/hash/cache
перевірок і сценаріїв revoke/void. Це зафіксовано в
[130 — Публічні вкладення паспорта](../backlog/130-public-passport-media.md).

Будь-яке інше нове поле для паспорта також має пройти такий порядок:

1. Погодити, чи воно справді публічне, а не лише зручне в private detail.
2. Додати його до явної `PublicPassportView` allow-list проєкції, а не віддати
   ORM-модель або весь звіт.
3. Відобразити узгоджено у browser-паспорті й PDF; будь-яку виправдану
   різницю для передачі документа (як код або дата дослідження) зафіксувати
   явно.
4. Додати API/RBAC/regression тести, включно з reissue, revoke і void, якщо
   поле пов’язане з файлом або публічним URL.

## 8. Dashboard, дані та межі MVP

Dashboard використовує private `GET /reports`: server-side pagination, пошук,
фільтри й сортування. `sold=true|false` є зручною двостановою проєкцією
детального commercial status, а не його заміною. Звіт відкривається через
`/report-detail.html?id=<report_id>`.

Legacy `/diamonds/*` вилучено. Historical legacy-колонки не очищалися та не
перераховувалися; їхня безпечна доля окремо описана у
[120](../backlog/120-legacy-calculation-and-ml-boundary.md).

Поточні automated tests використовують SQLite у пам’яті для backend та mock
HTTP для Playwright. Вони перевіряють RBAC, lifecycle, allow-list, QR/PDF і
code lookup, але не замінюють повний real-browser E2E з MariaDB.
