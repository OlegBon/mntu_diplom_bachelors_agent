# Відновлення локальної MariaDB

Цей guide описує безпечний перехід Diamant ID з **поточного, вже
відновленого тимчасового XAMPP MariaDB** до чистого локального MariaDB
середовища. Він не є інструкцією для repair файлів таблиць у `mysql/data`.

## Коли застосовувати

Потрібен, якщо MariaDB аварійно завершується, має пошкоджені службові
Aria/InnoDB-таблиці або працювала через `innodb_force_recovery`. Інцидент
16 вересня 2026 року завершено: у тому самому XAMPP створено чистий
`mysql/data` зі штатного `mysql/backup`, а SQL-дампи відновлено й перевірено.
Старий data-directory збережено окремим аварійним архівом.

## Межі та гарантії

- Джерело даних для Diamant ID: `diamond_oltp`, `diamond_market`,
  `diamond_analytics`.
- `scripts/seed_db.py` **не** є способом відновлення: він руйнівно створює
  demo-набір.
- Alembic не потрібно запускати до імпорту: дамп відновлює наявну схему та
  `alembic_version` разом із даними.
- Не копіюйте вибірково `.frm`, `.ibd`, `.MAI`, `.MAD` чи інші файли таблиць
  між інсталяціями. Відновлення виконується лише через SQL-дамп.
- Не видаляйте й не перезаписуйте старий `mysql/data`, доки чистий сервер не
  пройде всі перевірки нижче.

## Фаза A — зафіксувати резервні копії

1. Переконайтеся, що поточний MariaDB запускається **без**
   `innodb_force_recovery` у конфігурації.
2. Перевірте підключення через консольний клієнт, не через phpMyAdmin:

   ```bat
   D:\DevTools\xampp\mysql\bin\mysql.exe --protocol=TCP -h 127.0.0.1 --port=3306 -u root -e "SELECT 1 AS connection_ok; SHOW DATABASES;"
   ```

3. Зробіть окремий дамп Diamant ID. Додавайте `-p`, якщо для локального
   користувача встановлено пароль; консоль запросить його без виведення:

   ```bat
   D:\DevTools\xampp\mysql\bin\mysqldump.exe -u root --databases diamond_oltp diamond_market diamond_analytics --routines --events --triggers --single-transaction --result-file="D:\DevTools\Backups\diamant-id-recovery-YYYY-MM-DD.sql"
   ```

4. Якщо потрібні інші локальні проєкти, експортуйте **кожну** їхню
   неслужбову базу окремо до переходу. Не експортуйте та не імпортуйте
   `mysql`, `performance_schema`, `information_schema` або `phpmyadmin` як
   спосіб перенесення інсталяції.
5. Перевірте, що створені SQL-файли існують, мають ненульовий розмір і не
   лежать усередині каталогу XAMPP `data`.

## Фаза B — створити чистий сервер

1. Зупиніть MariaDB у XAMPP штатною кнопкою **Stop**; переконайтеся, що
   `mysqld.exe` більше не працює.
2. Збережіть всю стару папку `mysql/data` як недоторканий аварійний архів в
   окремому каталозі на тому самому або іншому диску. Не видаляйте її.
3. Підготуйте чисту інсталяцію MariaDB/XAMPP: найпростіше — нову папку
   XAMPP або заново ініціалізований **новий** data-directory. Її версію та
   порт потрібно зафіксувати до імпорту; для Diamant ID лишається MariaDB,
   не MySQL іншого діалекту.
4. Запустіть чистий MariaDB та перевірте `SELECT 1`. До імпорту не
   використовуйте старий каталог `data` і не відкривайте стару phpMyAdmin
   storage database.

## Фаза C — імпорт Diamant ID

Імпортуйте дамп у **чистий, порожній** MariaDB лише після окремого
підтвердження, що цільовий сервер правильний:

```bat
D:\Path\To\Clean-XAMPP\mysql\bin\mysql.exe -u root < "D:\DevTools\Backups\diamant-id-recovery-YYYY-MM-DD.sql"
```

Якщо шлях або порт чистого сервера відрізняється, спочатку перевірте його
командою `SELECT 1`; не припускайте, що він збігається зі старим XAMPP.
Після імпорту зробіть новий дамп уже з чистого сервера — це контрольна точка
rollback для подальших змін.

## Фаза D — верифікація Diamant ID

Усі команди нижче є read-only, крім запуску застосунку:

```powershell
.\.venv\Scripts\python.exe -m alembic -c alembic.ini current
.\.venv\Scripts\python.exe -c "from backend.main import app; print(app.title)"
```

Далі вручну:

1. Запустіть backend і frontend за [local-start.md](../local-start.md).
2. Увійдіть під admin та експертом.
3. Перевірте список звітів, один наявний detail/edit draft і вкладення, якщо
   вони є. Файли з `MEDIA_STORAGE_PATH` або `storage/reports` не входять до
   SQL-дампу: переносьте їх окремою копією лише після перевірки шляху.
4. Лише після успішного smoke-flow допустимо застосовувати наступну Alembic
   migration за окремим погодженням.

## Rollback

Якщо імпорт або перевірка неуспішні, зупиніть роботу з новим data-directory
і не видаляйте старий архів. Повернення означає лише зміну активного
локального MariaDB на старий аварійний data-directory; відновлювати файли
таблиць вручну не потрібно. Діагностика невдалого імпорту виконується
за текстом помилки та на копії дампу, а не повторними repair-операціями над
єдиним носієм даних.

## Після завершення

Оновіть приватний `.env`, якщо змінилися лише host/port/name локального
сервера, без запису секретів у Git. Потім зафіксуйте версію MariaDB, шлях
backup і результати smoke-перевірок у `docs/progress.md`; самі дампи та
локальні медіафайли до репозиторію не додаються.
