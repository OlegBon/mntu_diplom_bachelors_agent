# ⚙️ Diamant ID — технічний опис і актуальний статус

Diamant ID — дипломний вебзастосунок для ведення експертних звітів про діаманти, роботи з довідниками якості, розрахунку оцінок огранювання за правилами IDC та демонстраційного прогнозу ціни.

Цей документ фіксує **фактично реалізований локальний MVP**, його технічні межі та обов’язкові умови наступних етапів. Деталі структури коду й API наведено в [architecture.md](./architecture.md), інструкція запуску — у [local-start.md](./local-start.md), а послідовність робіт — у [work_plan.md](./work_plan.md).

> **Статус на 13 вересня 2026.** Локальний MVP працює на FastAPI, SQLAlchemy та MariaDB/XAMPP; frontend зібрано на Gulp, Pug, SCSS і vanilla JavaScript. Є JWT-вхід, ролі, звіти, ринкові довідники, IDC-розрахунок і евристичний прогноз ціни. Це ще не production-система: Docker, PostgreSQL, версіоновані міграції, реальна ML-модель, повний набір тестів і публічний deployment не реалізовані.

## 1. Можливості MVP

### Звіти про діаманти

- Створення звіту з параметрами форми, 4C, геометрії, пропорцій, finish та походження каменю.
- Автоматична генерація ідентифікатора звіту у форматі `DR-00001`.
- Перегляд окремого звіту та списку звітів із пагінацією, пошуком за ID, фільтром стану й сортуванням.
- Оновлення ціни та статусу продажу, видалення звіту для адміністратора.
- Підтримка полів для зображення plotting і реального фото в моделі даних; завантаження та файлове сховище ще не реалізовані.

### Розрахунок якості та ціни

- `DiamondCalculator` оцінює `proportions_grade` для Round Brilliant за table, depth, crown і pavilion.
- Підсумковий `cut_grade` дорівнює найгіршій з оцінок proportions, polish і symmetry.
- Якщо ціна не задана, `MLService` бере останній ринковий індекс і застосовує евристичну формулу для carat, color, clarity та cut.
- Результат `MLService` має випадкову варіацію і є демонстраційним прогнозом, а не результатом навченої, відтворюваної ML-моделі.

### Користувачі та доступ

- Вхід через `POST /token` з отриманням JWT Bearer token.
- Ролі `admin` і `gemologist`.
- Admin керує користувачами та може змінювати ринковий індекс; авторизований експерт створює звіти.
- API перевіряє токен у protected маршрутах; frontend зберігає token у `localStorage`.

### Ринок і статистика

- Довідники shape, color, clarity, cut, polish, symmetry, proportions, fluorescence та origin зберігаються в `grade_mappings`.
- Поточний індекс ціни та історія його оновлень зберігаються в `market_price_reference`.
- API повертає агреговану статистику кількості звітів і середньої ваги каменів за експертами.

## 2. Реалізований технологічний стек

| Зона | Технології та призначення |
| --- | --- |
| Backend/API | Python 3.13, FastAPI, Uvicorn, Pydantic 2 |
| Дані | SQLAlchemy 2, MariaDB через `mysql-connector-python`; локально — XAMPP |
| Безпека | JWT (`python-jose`), `passlib`/bcrypt; поточний seed має технічний борг відкритих тестових паролів |
| Доменна логіка | Власний IDC-калькулятор і евристичний `MLService` |
| Frontend | Gulp 5, Pug, SCSS/Sass, vanilla JavaScript, BrowserSync |
| Дані для seed | Pandas і `data/diamonds_dataset.csv` |
| Перевірки | Локальний Node.js API-аудитор без запису даних; повноцінні pytest/E2E ще відсутні |
| Документація агента | `AGENTS.md`, `.codex/rules`, `.codex/skills` |

Залежності зафіксовано в `requirements.txt` і `frontend/package-lock.json`. Оновлення версій виконуються адресно після перевірки сумісності; масове автоматичне оновлення залежностей без тестового контуру не є допустимою заміною такого рев’ю.

## 3. Локальне середовище та інфраструктура

### Локальна розробка

Поточний робочий контур складається з трьох процесів/компонентів:

```text
BrowserSync / Gulp (:3000 або вільний порт)
             │ HTTP JSON + Bearer JWT
             ▼
FastAPI / Uvicorn (:8000)
             │ SQLAlchemy
             ▼
MariaDB / XAMPP (:3306)
```

- Backend запускається з кореня репозиторію: `python -m uvicorn backend.main:app --reload`.
- Frontend збирається через `npm run build`, а режим розробки запускається `npm start` із `frontend`.
- CORS дозволяє локальні origin `localhost` і `127.0.0.1` з довільним портом, тому BrowserSync може обрати інший вільний порт.
- Swagger UI доступний на `http://127.0.0.1:8000/docs`.

Повний сценарій відтворення віртуального середовища та запуску розміщено в [local-start.md](./local-start.md).

### Локальні дані

`scripts/seed_db.py` перестворює бази `diamond_oltp` і `diamond_market`, створює `diamond_analytics`, формує SQLAlchemy-таблиці й завантажує тестові дані. Це руйнівна операція, яка дозволена лише для локальної тестової MariaDB.

Перед seed слід переконатися, що підключення спрямоване на локальний XAMPP і дані можна втратити. Скрипт не призначений для майбутнього PostgreSQL або публічного середовища.

### Локальний API-аудит

Після запуску API доступна команда:

```powershell
cmd /c "cd frontend && npm run audit:api"
```

Вона перевіряє лише локальний HTTP API, виконує безпечні GET-запити та CORS preflight, не виконує login, мутацій, seed або запитів із токеном. Звіт створюється локально в `docs/audits/` і не потрапляє в Git.

## 4. Дані, API та межі доступу

### Логічні бази MariaDB

| База | Таблиці / призначення | Статус |
| --- | --- | --- |
| `diamond_oltp` | `experts`, `diamond_reports`: користувачі й оперативні звіти | Реалізовано |
| `diamond_market` | `grade_mappings`, `market_price_reference`: довідники й індекс | Реалізовано |
| `diamond_analytics` | Майбутні результати ML та аналітика | Лише зарезервовано seed-скриптом |

### Основні API-групи

| Група | Призначення | Доступ |
| --- | --- | --- |
| `/token` | Вхід і видача JWT | Публічний |
| `/diamonds/` | Звіти: список, пошук, створення, оновлення, видалення | Залежить від операції |
| `/users/`, `/users/me`, `/experts/` | Користувачі, поточний профіль, експерти | Захищений; керування — admin |
| `/market/mappings` | Довідники для форм | Публічний |
| `/market/price` | Поточний індекс та його оновлення | Читання публічне, запис — admin |
| `/statistics/expert-performance` | Статистика експертів | Поточний публічний маршрут |

FastAPI автоматично формує OpenAPI-контракт у `/openapi.json` та Swagger UI у `/docs`. Контракт перевіряється локальним аудитом, але це не скасовує потребу в API-тестах із ізольованою БД.

## 5. Політика конфігурації та безпеки

- Секрети, параметри БД і JWT-ключі зберігаються лише в локальному `.env` або захищеному env-сховищі майбутнього провайдера; їх не можна комітувати або цитувати в документації.
- Потрібно додати безпечний `.env.example` з іменами змінних без реальних значень.
- `SECRET_KEY` має бути обов’язковим і унікальним для кожного середовища; fallback-значення з коду треба прибрати до публічного запуску.
- Seed-паролі необхідно замінити bcrypt-хешами. Поточне порівняння відкритого пароля призначено винятково для історичного локального MVP.
- JWT у `localStorage` доречний лише як поточна MVP-реалізація. Перед production потрібне окреме рішення щодо XSS-захисту, строків життя токенів, logout/revocation та, за потреби, HttpOnly-cookie-сесій.
- Production CORS має дозволяти лише точні HTTPS-домени frontend, а не широкий regex локальної розробки.

## 6. Планований PostgreSQL і тестовий домен

Цільовий напрямок не є частиною поточного runtime:

| Зона | Поточний стан | Наступний етап |
| --- | --- | --- |
| Локальна БД | MariaDB/XAMPP | Залишається основою розробки до окремої міграції |
| Production БД | Відсутня | PostgreSQL, імовірно Supabase або managed PostgreSQL |
| Backend | Локальний Uvicorn | Docker-контейнер на обраному провайдері після перевірки обмежень |
| Frontend | BrowserSync static build | Статичний `dist` на shared hosting або іншому static hosting |
| Міграції | Відсутні | Alembic, версіонування, backfill, перевірка цілісності та rollback |

Перед публічним запуском обов’язкові: PostgreSQL-рев’ю SQLAlchemy-моделей, ізольований seed/імпорт, health-check, HTTPS/TLS, точний CORS, захищені secrets, ручний smoke-flow і план backup/restore. Вибір Back4App, Render, Supabase чи іншого провайдера потребує окремого рішення та перевірки обмежень у момент розгортання.

## 7. Що ще не є готовим

1. Безпечна конфігурація: `.env.example`, обов’язковий `SECRET_KEY`, явний `DATABASE_URL`.
2. Bcrypt-дані для seed і повне security hardening auth/JWT.
3. Надійний seed із чистої MariaDB та звірка фактичної схеми.
4. Завершена frontend ↔ API інтеграція для списку, пошуку, створення та редагування звітів.
5. Рев’ю RBAC і незавершеного `/experts/`.
6. Таблиці `diamond_analytics`, відтворювана ML-модель, підготовка даних та оцінка якості прогнозу.
7. `pytest` unit/API/integration тести та frontend smoke/E2E сценарії.
8. PostgreSQL-міграції, Docker і тестовий deployment.

Пріоритети, критерії готовності та деталізація цих пунктів підтримуються у [work_plan.md](./work_plan.md).
