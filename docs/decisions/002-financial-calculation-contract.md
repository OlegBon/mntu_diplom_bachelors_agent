# ADR-002: фінансовий контракт і межі demo-прогнозу

**Статус:** погоджено для локального MVP  
**Дата:** 2026-09-14  
**Пов’язані задачі:** [037 — фінансові розрахунки](../work_plan.md), [040 — ядро звіту](../backlog/040-report-core-and-reference-data.md)

## Контекст

Поточний `DiamondReport.price` має тип `DECIMAL(12,2)`, але не має сталої семантики. Він може бути введений frontend-майстром, обчислений browser-формулою або заповнений `MLService`. Паралельно `diamond_market.market_price_reference` зберігає число `6000.0000`, однак для нього не визначені джерело, валюта й одиниця. Це технічна fallback-константа, обрана без зовнішнього ринкового джерела.

`MLService` є демонстраційною евристикою з випадковим коефіцієнтом. Він не є навченою ML-моделлю, експертною оцінкою чи ринковим котируванням.

## Рішення

### Поточні дані

1. Поточний `diamond_reports.price` вважається `legacy_unclassified_value`. Його не перейменовують і не переносять автоматично; виняток для локальної demo-вітрини описано нижче. Значення не подаються як «ринкова», «експертна» або «фактична» ціна.
2. `market_price_reference.price_index_value`, зокрема `6000`, — лише **технічний довідковий індекс demo-евристики**. До появи перевіреного джерела він не має валюти, одиниці виміру, статусу ціни за карат або ринкового котирування.
3. Результат `MLService` називається **системним демонстраційним прогнозом**. Він не впливає на видачу звіту, публічний паспорт, факт продажу або експертний висновок.

### Виняток: локальна demo-вітрина звітів

Для наочного локального dashboard дозволено показувати непорожній legacy `price` у колонці **«Ціна»** лише для початкового demo-набору `diamonds_dataset.csv`:

- набір містить 1 000 записів за період **01.01.2023–31.12.2025**;
- UI показує значення як `USD <сума> d`, де `d` — видима й доступна позначка **demo**;
- натискання на значення пояснює тип, джерело, дату запису та період набору, а також прямо зазначає, що це не актуальне ринкове котирування;
- умовне `USD` — домовленість для відображення саме цього demo-набору, а не властивість поточної універсальної моделі `price`;
- порожнє значення показується як `—`, без demo-позначки;
- ці значення не потрапляють до публічного паспорта, не є ціною продажу й не перераховуються після зміни валюти або ринкового довідника.

Для реальних даних потрібна окрема модель із типом ціни, валютою, джерелом, датою фіксації та правилами історичного збереження. Порівняння зі свіжим курсом або ринком буде окремим аналітичним сценарієм, а не зміною історичного запису.

### Цільова модель для 040 і наступних задач

Окремі величини не змішуються в одному полі:

| Назва | Власник | Сенс | Мінімальні метадані |
| --- | --- | --- | --- |
| `market_reference` | джерело ринкових даних | підтверджена довідкова величина | сума, валюта, одиниця, джерело, дата |
| `system_prediction` | система | розрахунок правилами або версіонованою ML-моделлю | сума, валюта, версія правила/моделі, inputs, дата |
| `expert_appraisal` | експерт | задокументована професійна оцінка | сума, валюта, експерт, дата, примітка |
| `asking_price` | пропозиція каменю | ціна, за якою камінь пропонується | сума, валюта, дата початку, статус |
| `sale_price` | подія продажу | підтверджений факт операції | сума, валюта, дата продажу, джерело |

`sale_price` є необов’язковим: продаж не є обов’язковою властивістю нового звіту чи каменю. Комерційний статус каменю окремо має значення `not_for_sale`, `available`, `reserved`, `sold`, `withdrawn`.

## Точність та межі реалізації

- У серверній доменній логіці суми використовують `Decimal`, у БД — `Numeric`/`DECIMAL`; через API вони не передаються як `float`.
- Округлення відбувається лише в явно визначеній операції або на UI-межі. Для кожної майбутньої суми окремо фіксуються масштаб, режим округлення і валюта.
- Frontend може показувати попередній розрахунок, але не є джерелом істини для збереженої суми. Остаточне обчислення і валідація належать backend.
- Публічний паспорт не показує жодну з цих сум, доки окрема політика не визначить безпечне виняткове поле.

## Наслідки та наступні кроки

037 не змінює поточну MariaDB-схему, OpenAPI або історичні записи. У 040 потрібно окремо погодити Alembic-міграцію, API-контракти, точність і тестові приклади; лише після цього можна створювати нові поля або backfill. Тести 040 мають покривати `Decimal`, правила округлення, відхилення невалідних сум та межу між системним прогнозом, експертною оцінкою і продажем.
