# ADR-003: реалізація ядра звіту та перенесення legacy-даних

**Статус:** погоджено для реалізації локального MVP  
**Дата:** 2026-09-14  
**Пов’язані документи:** [ADR-001](./001-report-domain-contract.md), [ADR-002](./002-financial-calculation-contract.md), [040 — ядро звіту](../backlog/040-report-core-and-reference-data.md)

## Контекст

`diamond_oltp.diamond_reports` зараз поєднує дані фізичного каменю, версію
експертного висновку, простий статус продажу та число `price` без сталої
семантики. Локальний CSV і MariaDB seed містять 1 000 синтетичних записів,
створених для статистичних і майбутніх ML-експериментів. Вони є корисним
історичним набором для розробки, але не підтвердженим навчальним або ринковим
джерелом.

Read-only перевірка `data/diamonds_dataset.csv` 2026-09-14 показала:

- 1 000 унікальних `report_id`;
- усі записи мають legacy `price`;
- 707 записів мають `is_sold=true` і `sale_date`, 293 — ні;
- `stone_origin` містить коди `0`, `1`, `2`, `3`, хоча поточний seed-довідник
  пояснює лише `0=Natural` та `1=Lab-Grown`.

Отже, коди `2` і `3` не можна автоматично трактувати як природні, лабораторні
або оброблені камені.

## Рішення

### 1. Безпечний перехід моделі

Застосовуємо **expand–contract**, а не руйнівне перейменування:

```text
Stone ──< DiamondReport ──< ReportEvent
  └──< StoneValuation
```

- `Stone` отримує технічний `stone_id` і зберігає сталі фізичні дані: форму,
  4C, виміри, пропорції та параметри походження/ідентифікації.
- Наявний `DiamondReport.report_id` лишається незмінним бізнес-ідентифікатором.
  До таблиці додаються `stone_id`, lifecycle-поля, автор і видавець.
- Старі колонки `diamond_reports` не вилучаються в цій задачі. Вони лишаються
  compatibility-даними для чинного frontend і `/diamonds/*` до його поетапного
  переходу на новий API.
- `ReportEvent` є append-only журналом створення та зміни статусу.
- `StoneValuation` має чіткий тип суми, `Numeric`/`Decimal`, валюту, джерело,
  час і автора. Жоден legacy `price` до нього не переноситься автоматично.

Ця модель дозволяє одному каменю мати кілька звітів у майбутньому, але backfill
першої версії створює один `Stone` на один існуючий звіт: зараз немає надійного
ідентифікатора, щоб з’єднати різні legacy-звіти в один фізичний камінь.

### 2. Backfill 1 000 legacy-записів

Alembic revision має бути ідемпотентною в межах одного застосування й робити
таке:

| Legacy-дані | Цільове значення | Причина |
| --- | --- | --- |
| Кожен `diamond_reports` | один `Stone`, прив’язаний через `stone_id` | Зберігає всі наявні записи без припущення про спільний камінь. |
| `stone_origin=0` | `origin=natural`, `identification_status=preliminary` | Єдине задокументоване безпечне зіставлення. |
| `stone_origin=1` | `origin=lab_grown`, `identification_status=preliminary` | Єдине задокументоване безпечне зіставлення. |
| `stone_origin=2` або `3` | `origin=unknown`, legacy-код зберігається | Семантика кодів не підтверджена. |
| Усі старі звіти | `status=draft`, event `legacy_import` | Їх не можна вважати виданими чи публічними. |
| `is_sold=true` | `market_status=sold`, `legacy_sale_date` | Зберігаємо технічний історичний стан, але не створюємо факт продажу з ціною. |
| `is_sold=false` | `market_status=not_for_sale` | Намір пропозиції на ринку не доведений. |
| `price`, `days_on_market`, image-path колонки | лишаються legacy-даними | Не переозначати без підтвердженого джерела, дати початку чи файлу. |

Для імпорту застосовується технічне поле provenance (`legacy_source_report_id`),
а не евристика за 4C. Це робить backfill перевірюваним і не заважає створювати
нові `Stone` без legacy-походження.

### 3. Стани, експертні та розрахункові результати

Новий звіт має статуси `draft → review → issued → void` згідно з ADR-001.
Переходи, author/admin RBAC і причина переходу фіксуються через `ReportEvent`.

У звіті окремо зберігаються:

- системні `system_proportions_grade`, `system_cut_grade`, версія правила;
- експертні `expert_proportions_grade`, `expert_cut_grade`, час підтвердження.

Автоматичний результат не є експертним підтвердженням. `issued` можливий лише
після явного підтвердження необхідних експертних полів; imported legacy-звіти
залишаються чернетками, доки їх не переглянуть вручну.

### 4. API та сумісність

У цій задачі створюється новий приватний `/reports` API для доменної моделі:
список/деталь, draft-створення, редагування draft, transitions, події та
довідники. Gemologist бачить і редагує лише власні чернетки; admin бачить усі,
керує review/issued/void, але не створює первинний звіт.

Чинний `/diamonds/*` тимчасово не перейменовується і не отримує нової
семантики: він зберігає сумісність із наявними dashboard і create-form. UI
переходить на `/reports` у задачах 060–080, після чого legacy-маршрути можна
окремо позначити deprecated і вилучити погодженою міграцією.

### 5. Довідники й майбутні ринкові ціни

Текстові контрольовані значення (статуси звіту, походження, обробка,
ідентифікація, комерційний статус і форми) зберігаються в окремому серверному
довіднику з кодом, міткою, порядком і ознакою активності. Числові grade
mappings лишаються сумісними з чинним `diamond_market.grade_mappings`.

Майбутня ціна з авторитетного провайдера створюється окремим versioned market
reference/valuation record з джерелом, датою, валютою, одиницею і правилами
оновлення. Спочатку це буде ручна admin-дія; scheduler додається лише після
вибору постачальника, ліцензії, rate limit та політики помилок. Він не
перезаписує `DiamondReport.price`.

## Наслідки

- Поточні 1 000 записів зберігаються для статистики, UI та міграційних тестів.
- Їхня придатність для ML не декларується: окремо потрібні опис походження,
якість, train/validation split і метрики.
- Згодом потрібен детермінований `seed v2`: окремо від dataset, з відтворюваною
генерацією та новими полями. Це не змінює чинний seed у межах цієї revision.
- `alembic upgrade` локальної MariaDB виконується тільки після окремого
підтвердження користувача; до нього міграція перевіряється на ізольованій БД і
через generated SQL.
