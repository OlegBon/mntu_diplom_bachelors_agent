# Web Performance

## Коли застосовувати

Застосовуй на запит performance-аудиту, перевірки Core Web Vitals або перед deployment. Не використовуй її як привід змінювати код чи інфраструктуру без окремого запиту.

## Методика

1. Зафіксуй середовище, URL, версію збірки та спосіб вимірювання. Локальний Gulp-server не є production-виміром.
2. Збери лише відтворювані факти: frontend-збірку, розміри ресурсів, browser-навігацію за доступності інструменту, HTTP-час API, логи або план SQL-запиту.
3. Проаналізуй чотири рівні: клієнт (JS/CSS/зображення/DOM), мережа (кеш, стиснення, TLS, CORS), сервер (FastAPI/серіалізація) і БД (SQLAlchemy, індекси, N+1, пагінація).
4. Для майбутнього тестового домену окремо оцінюй розміщення FastAPI, PostgreSQL, статичного frontend, CDN і мережеву відстань. Не видавай план deployment за вже налаштований контур.

## Інтерпретація

- Цільові орієнтири: LCP < 2.5 с, INP < 200 мс, CLS < 0.1. Не заявляй ці значення без вимірювання.
- Явно позначай кожний висновок як `виміряно`, `спостережено в коді` або `припущення`.
- Для критичного SQL-запиту запропонуй `EXPLAIN (ANALYZE, BUFFERS)`, але не запускай його без дозволу, якщо це може зачепити реальну БД.

## Формат результату

Подай Diagnostic Matrix: рівень, факт/ризик, метрика, вплив і критичність. Після неї наведи Action Plan у пріоритетному порядку, де кожна дія містить очікуваний ефект і спосіб перевірки. За запитом на формальний аудит зберігай звіт у `docs/audits/`, не створюючи штучних метрик.
