# Тестування Python

## Коли застосовувати

Застосовуй для створення test suite, `pytest`-тестів, рев’ю покриття та планування тестової інфраструктури.

## Стратегія

1. Unit: `DiamondCalculator`, перетворення даних і сервіси без реальної БД.
2. API: FastAPI routes, Pydantic-валідація, auth і RBAC через test client.
3. Integration: SQLAlchemy з ізольованою тестовою БД; не використовуй локальні XAMPP-дані користувача.
4. E2E: після інтеграції фронтенду перевір login і життєвий цикл звіту.

Починай з unit-тестів для детермінованих IDC-правил. API та integration-тести не повинні залежати від особистих даних чи поточної MariaDB у XAMPP.

## Правила

- Один тест перевіряє одну поведінку; назва описує очікуваний результат.
- Застосовуй fixtures для даних, test client і session; кожен тест самостійний і прибирає власний стан.
- Межі шкал, пусті/некоректні вхідні дані, auth-помилки та заборонені ролі — обов’язкові негативні сценарії.
- Зовнішні ресурси, поточний час і випадковість мокуй. `random` у ML-імітації не повинен робити unit-тести flaky.
- Позначай тести маркерами `unit`, `api`, `integration`; повільні залежні тести не запускай у базовому швидкому наборі.

## Fixtures і межі середовища

- Створюй фабрики тестових користувачів, звітів і ринкових даних замість копіювання великих фрагментів між тестами.
- Test client має отримувати окрему dependency для сесії БД. Кожен тест створює й прибирає власний стан транзакцією або ізольованою БД.
- Не викликай `seed_db.py` у тестах: він руйнівний і не є test fixture.
- Для JWT перевіряй не лише успішний login, а й відсутній, прострочений або змінений токен, доступ різних ролей та спробу змінити чужий ресурс.

## Сценарії першої черги

1. Межі пропорцій, округлення та класи IDC у `DiamondCalculator`.
2. Валідація Pydantic: відсутні поля, некоректні числа й недопустимі значення.
3. Auth/RBAC: login, 401, 403, `users/me`, створення і видалення користувачів.
4. CRUD звітів: створення, фільтри, пагінація, доступ і граничні значення.
5. Ринкові довідники та ML-імітація з фіксованим джерелом випадковості.

## Мінімальна майбутня конфігурація

Після погодження додай `pytest`, `pytest-cov`, `pytest.ini` або секцію в `pyproject.toml`, структуру `tests/{unit,api,integration}` і команду для всього набору. Ціль покриття визначається після базового вимірювання; критичні шляхи auth, RBAC і IDC-розрахунків тестуються першими.

## Перед завершенням

Запускай лише релевантні тести, фіксуй команду й результат у `docs/progress.md`. Не змінюй production seed або локальну БД для виконання unit-тестів.
