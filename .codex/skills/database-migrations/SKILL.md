# Database Migrations

## Коли застосовувати

Застосовуй лише під час зміни схеми, масового backfill або планування MariaDB → PostgreSQL. Поточна runtime-БД — локальна MariaDB; PostgreSQL і Alembic ще не впроваджені.

## Планування

1. Прочитай моделі, CRUD-код, seed, пов'язані API-схеми та чинну документацію.
2. Визнач, чи змінюється структура, дані, індекс, тип поля або поведінка видалення. Оціни обсяг даних, блокування, сумісність MariaDB/PostgreSQL і можливість відкату.
3. Для змін, сумісних зі старим кодом, застосовуй expand-contract: додай сумісну структуру, перенеси або синхронізуй дані, перевір, а лише потім зроби поле обов'язковим чи прибери застаріле.
4. Для backfill підготуй ідемпотентний сценарій, критерії успіху, пакетну обробку, журналювання та rollback. Не маскуй backfill у старті застосунку.

## Майбутня PostgreSQL-міграція

План має охопити `DATABASE_URL`, драйвер, версіоновані Alembic-міграції, перенесення довідників і звітів, перевірку кількості та цілісності даних, smoke-тест API, deployment і rollback. Особливо звіряй `DECIMAL`, enum-значення, часові поля, автоінкрементні ключі та SQL-діалекти.

## Дозволи й результат

Не запускай SQL, seed, Alembic або інші команди, що змінюють дані чи схему, без прямого дозволу користувача. Після дозволеної операції онови схему БД, архітектуру за потреби й `docs/progress.md`; у звіті вкажи виконані кроки, перевірки, ризики та спосіб відкату.
