# Патерни Python

## Коли застосовувати

Застосовуй під час написання, рев’ю або рефакторингу Python-коду, зокрема FastAPI-роутів, Pydantic-схем, SQLAlchemy-моделей, сервісів і скриптів.

## Основні принципи

- Обирай читабельність і явність замість складних скорочень.
- Для нового або зміненого коду використовуй сучасні типи (`list[str]`, `dict[str, object]`, `T | None`) і docstring для публічної доменної логіки.
- Імпорти розміщуй у порядку: stdlib, сторонні бібліотеки, локальні модулі.
- Лови конкретні винятки та зберігай першопричину через `raise ... from error`; не використовуй bare `except`.
- Використовуй `with` та FastAPI dependencies для керування ресурсами. Сесія SQLAlchemy закривається незалежно від результату запиту.
- Не використовуй змінювані значення за замовчуванням; перевіряй `None` через `is None`.

## FastAPI та SQLAlchemy

- Валідуй request через Pydantic, відповідь — через явну response schema.
- Не змішуй HTTP-деталі з SQL і правилами IDC: router → `crud.py`/service → модель БД.
- Всі операції зміни даних проходять server-side auth/RBAC.
- Запити будуй через SQLAlchemy або параметри драйвера; ніколи рядковою інтерполяцією SQL.
- Відкривай і закривай SQLAlchemy-сесію через поточну dependency. Не створюй новий engine або sessionmaker всередині маршруту.
- Для списків визначай межі `limit`, перевіряй допустимість полів сортування та не передавай довільний клієнтський рядок у вираз SQLAlchemy.

## Помилки й контракти

- Відрізняй помилку валідації (422), відсутній ресурс (404), відсутність автентифікації (401) і заборону ролі/дії (403). Не маскуй їх одним 500.
- Не повертай traceback, деталі підключення або інші внутрішні дані клієнту. Логування не повинно містити паролів чи токенів.
- Зміна поля в `schemas.py` є зміною API-контракту: перевір backend-маршрут, frontend-виклик і сумісність з наявними даними.

## Доменна логіка

- Розрахунки мають бути детермінованими за однакових вхідних даних. Якщо випадковість потрібна для seed або ML-імітації, ін’єктуй або фіксуй джерело випадковості для тестів.
- Пороги IDC описуй іменованими константами або таблицями правил, коли логіка розширюється; перевіряй межі діапазонів тестами.
- Не приховуй fallback-значення для бізнес-даних без явного журналювання чи документації.

## Скрипти

- Скрипти в `scripts/` мають явно описувати, які дані читають або змінюють. Руйнівний `seed_db.py` запускай тільки за прямим дозволом.
- Не виконуй важкий backfill під час імпорту модуля або старту FastAPI. Для нього потрібен окремий відновлюваний сценарій.

## Перед завершенням

Перевір імпорт застосунку, форматування та відсутність секретів у diff. Для зміненої поведінки застосуй `python-testing` і додай або заплануй релевантний тест.
