# Security Review

## Коли застосовувати

Застосовуй на запит аудиту безпеки або перед зміною auth, RBAC, JWT, CORS, API, обробки файлів чи чутливих даних. Звичайна зміна стилів не потребує цієї навички.

## Межі перевірки

- Не розкривай і не копіюй значення `.env`, токенів, паролів, JWT або рядків підключення.
- Не запускай seed, не змінюй користувачів, не відкликай токени та не роби атакувальних перевірок без окремого дозволу.
- Відокремлюй доведений факт від ризику та рекомендації; відсутність тесту не доводить відсутність уразливості.

## Порядок аудиту

1. Перевір секрети в tracked-файлах, логах, документації та прикладах конфігурації, не виводячи їхні значення. `SECRET_KEY` має бути обов'язковим поза локальною розробкою.
2. Прочитай `backend/security.py`, auth-маршрути й захищені endpoints: bcrypt-хешування, строк JWT, коректні 401/403, server-side перевірку ролей і прав на конкретний ресурс.
3. Перевір Pydantic-валідацію, параметризацію SQLAlchemy, безпечні повідомлення про помилки, обмежений CORS і відсутність довіри до `localStorage` як джерела прав.
4. Перевір frontend на небезпечний `innerHTML`, зовнішні посилання, введення файлів та витік технічних деталей у UI.
5. Перевір seed окремо: це тільки локальний інструмент, не production-механізм. Познач демо-облікові дані як ризик, якщо вони можуть потрапити в публічний контур.
6. Виконай доступний dependency-аудит лише коли це погоджено й команда безпечна для поточного середовища.

## Формат результату

Для кожного пункту подай `Критично`, `Високо`, `Середньо`, `Низько` або `Інформаційно`, файл/маршрут, доказ без секретів, ризик і конкретне виправлення. Окремо зазнач неперевірені частини та команди, які не запускалися.
