# Локальні правила: фінансові розрахунки

## Призначення

Ці правила застосовуються до ціни, прогнозу, експертної оцінки, факту продажу,
валюти, ринкових довідників та будь-яких сум у Diamant ID. Вони не замінюють
правила для фізичних вимірів каменю: каратність, міліметри, відсотки proportions
та оцінки 4C мають власну точність і одиниці.

## Єдина термінологія

Не змішуйте в одному полі або підписі різні за змістом величини:

- **ринкова довідкова ціна** — значення із `diamond_market` з джерелом і датою;
- **системний прогноз** — відтворюваний результат моделі або формули, а не
  сертифікована оцінка;
- **експертна оцінка** — значення, підтверджене експертом;
- **ціна продажу** — факт операції, який може бути відсутнім для не проданого
  каменю.

Кожне нове значення ціни повинно мати явно визначені тип, валюту, одиницю,
джерело та момент актуальності. Інтерфейс не повинен називати демо-прогноз
"ринковою" або "остаточною" ціною.

## Точність і зберігання

- У Python фінансові обчислення виконуйте через `decimal.Decimal`; не створюйте
  `Decimal` із `float`, а лише з рядка або цілого числа.
- У БД використовуйте `DECIMAL` / SQLAlchemy `Numeric`, а не `FLOAT` чи
  `DOUBLE`. Масштаб, точність і канонічна одиниця ціни визначаються окремим
  контрактом до зміни схеми.
- Не передавайте фінансове значення через `float` між ORM, сервісом, Pydantic і
  API. Узгоджене рядкове або Decimal-представлення має зберігати точність.
- Округлюйте лише на явно заданій межі: правилі домену, розрахунку валюти або
  відображенні. Правило, режим округлення та кількість знаків не приховуйте в
  UI або випадковому helper-і.

## Frontend та API

- У браузері суми з форми залишаються рядками до серверної валідації; `number`
  JavaScript не є джерелом істини для грошових обчислень.
- Live preview може пояснювати орієнтовний результат, але фінальне значення
  розраховує та валідує backend.
- Форматування валюти (`Intl.NumberFormat`) застосовуйте тільки на межі UI,
  після отримання канонічного значення, валюти та потрібної локалі.

## Джерела, моделі й зміни

- Ринкові дані надходять через виділений шар даних; не дублюйте ціни,
  коефіцієнти або grade mappings у Pug, SCSS чи клієнтському JavaScript.
- Демо-евристика `MLService` не є фінансовою моделлю. Справжній прогноз потребує
  версії моделі, набору вхідних даних, джерела, дати та відтворюваних тестів.
- Нову формулу, нову валюту, зміну масштабу `DECIMAL` або backfill історичних
  цін плануйте окремо: з версіонованою міграцією, перевіркою даних і rollback.
  Не запускайте міграцію чи backfill без окремого дозволу користувача.

## Перевірки

- Unit-тести фіксують точні приклади, межі та правила округлення.
- API-тести перевіряють контракт значення, валюти, джерела й відхилення
  невалідного вводу.
- Тести не маскують похибку переведенням очікуваного результату у `float`.
