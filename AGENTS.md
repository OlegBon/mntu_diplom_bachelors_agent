## MCP-сервери

MCP-сервери — необов’язкова можливість середовища, а не частина репозиторію. Їхній склад може відрізнятися між машинами та сесіями.

1. Джерело істини — інструменти, які активна сесія фактично надає агенту. Використовуй лише їх.
2. Якщо CLI доступний і налаштований, додатково звір конфігурацію командою `codex mcp list`. Помилка CLI або відсутність сервера не є приводом вигадувати його інструменти чи змінювати системну конфігурацію.
3. Не припускай назви серверів, методів або їхні можливості за старою документацією чи іншим проєктом. Перед викликом перевір доступний опис інструмента.
4. Обирай MCP лише коли він доречний задачі: документація бібліотеки, браузерне налагодження, E2E, GitHub-операції тощо. Для локальних файлів, Git або команд використовуй звичайні інструменти, якщо цього достатньо.
5. MCP не надає додаткових прав: секрети не розкриваються, а зовнішні зміни (push, PR, записи в сервісах) потребують дозволу користувача відповідно до правил проєкту.

Не підтримуй у цьому файлі статичний список «увімкнених» MCP-серверів: він швидко застаріває і не замінює фактичну конфігурацію сесії.

## Перевірка та документація

- Для Python-змін запускай релевантний import/smoke-check; для frontend — `npm run build`.
- Для UI-змін перевір відрендерену сторінку та один цільовий користувацький сценарій.
- Після завершення завдання оновлюй `docs/progress.md`: задача, файли, перевірки, нові env-змінні та обмеження. Новий запис додавай одразу під вступом у зворотному хронологічному порядку.
- Підтримуй `docs/work_plan.md` як актуальний перелік реалізованого й backlog. Оновлюй `docs/architecture.md` для зміни архітектури.

## Основні команди

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --reload
.\.venv\Scripts\python.exe scripts\seed_db.py
cmd /c "cd frontend && npm run build"
cmd /c "cd frontend && npm start"
cmd /c "cd frontend && npm run audit:api"
.\.venv\Scripts\python.exe -m pytest
cmd /c "cd frontend && npm test"
cmd /c "cd frontend && npm run test:e2e"
```

`seed_db.py` руйнівно перестворює локальні бази. Не запускай його без окремого підтвердження користувача. Якщо `npm.ps1` блокується execution policy, використовуй `cmd /c npm ...`, не змінюючи системну policy.

## Архітектурні завдання

Перед будь-якою архітектурною зміною прочитай `docs/architecture.md`.

- Поточний стек: FastAPI + SQLAlchemy 2 + MariaDB/XAMPP; Gulp + Pug + SCSS + JavaScript.
- Локальна база: `diamond_oltp`, `diamond_market`; `diamond_analytics` — запланований аналітичний шар.
- `local-dev` — база для локального MariaDB MVP; `main` — майбутній deploy-кандидат після перевіреної PostgreSQL-міграції.
- Не розгалужуй бізнес-логіку за Git-гілкою: відмінності середовищ належать до env, драйвера БД та міграцій.

## Життєвий цикл завдань і Git Workflow

Ти та будь-які твої субагенти ЗОБОВ'ЯЗАНІ суворо дотримуватися цього алгоритму, отримавши завдання розробити нову фічу, виконати рефакторинг або виправити баг.

### Крок 1: Ініціалізація та вибір режиму ізоляції

- **За замовчуванням** не пиши код напряму в захищених гілках (`main`, `master`, `dev`): спершу створи окрему гілку.
- **Виняток:** якщо користувач явно просить працювати без нової гілки або в поточній гілці, дотримуйся цієї вказівки.
- Перед початком роботи виклич інструмент читання файлів і перевір, чи існує файл `/docs/git-flow.md`.
  - **Якщо існує:** прочитай його. Використовуй описані там стандарти для назви гілок, структури комітів і префіксів (feat, bug, chore тощо).
  - **Якщо не існує:** використовуй стандартний підхід (наприклад, `feature/назва-завдання` або `fix/опис-бага`).
- Перед внесенням змін визнач режим своєї роботи:
  - **Сценарій А (паралельна робота субагентів):** якщо ти делегуєш завдання субагентам для паралельного виконання або система вже виконує інший процес у цій директорії, ти **ЗОБОВ'ЯЗАНИЙ використовувати Git Worktrees**. Кожен паралельний процес має працювати у своїй ізольованій папці на диску.
  - **Сценарій Б (одиночний/послідовний режим):** якщо ти працюєш над завданням сам і послідовно, використовуй стандартний флоу: просто створи гілку через `git checkout -b <branch-name>` у поточній директорії.

### Крок 2: Процес розробки (атомарні коміти)

- Працюй ітеративно (суворо в межах своєї гілки або папки worktree).
- Щойно ти успішно завершуєш великий логічний блок (налаштував схему даних, дописав контролер, тести пройшли успішно), ти **ЗОБОВ'ЯЗАНИЙ автоматично створити проміжний коміт**.
- Не чекай моєї команди для цих комітів. Це наша точка збереження (savepoint) для безпечного відкату.
- Пиши чіткі повідомлення комітів за стандартами проєкту.

### Крок 3: Завершення та рев'ю

- Коли ти виконав усі вимоги завдання й код працює, **ЗУПИНИСЯ**.
- Зроби фінальний коміт для своєї гілки.
- Надай мені короткий структурований звіт: які файли змінено та яку функціональність додано.
- Наприкінці звіту постав пряме запитання:
  - _Якщо використано Сценарій Б:_ «Фічу реалізовано. Перевіряємо роботу чи я можу виконати злиття (merge) з головною гілкою?»
  - _Якщо використано Сценарій А:_ «Ізольовану роботу завершено. Чи можу я злити гілку в main і видалити тимчасовий worktree?»
- **СУВОРА ЗАБОРОНА:** ніколи не виконуй `git merge`, не видаляй worktree і не створюй Pull Request без мого прямого текстового дозволу «Так, зливай».

## Тестування

- Backend: `pytest` з маркерами `unit`, `api`, `integration`; виконуй `\.venv\Scripts\python.exe -m pytest` або вибірково `-m unit` / `-m api`.
- API/integration-тести застосовують SQLite у пам’яті зі schema translation і не підключаються до XAMPP/MariaDB, не запускають `seed_db.py` та не використовують `.env`-облікові дані.
- Frontend: `cmd /c "cd frontend && npm test"` спершу збирає Pug/SCSS/JS, а потім запускає Node unit-тести модулів і jsdom DOM smoke.
- Browser: `cmd /c "cd frontend && npm run test:e2e"` запускає Playwright із тимчасовим BrowserSync і не викликає API. Chromium потрібно один раз встановити через `npx playwright install chromium chromium-headless-shell`.
- Базове покриття не є ціллю якості саме по собі; пріоритет — IDC, auth/RBAC, CRUD і граничні відповіді. Розширені flows login → dashboard → create → detail/edit додавати разом із відповідними UI-зрізами.
